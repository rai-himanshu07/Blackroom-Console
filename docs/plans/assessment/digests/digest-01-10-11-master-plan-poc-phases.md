### 01 — Remote Console — Project Master Plan

**1. Purpose & scope.** The foundational, top-of-stack specification: defines product mission, the narrow v1 platform target, five product principles (same-session-first, fail-closed, physical-privacy-as-security-property, remote-control-as-temporary-authority, independent-emergency-recovery), the four-component architecture, the authentication model, a *first-draft* state machine, physical display/input isolation requirements, browser/WebRTC/networking approach, security/production criteria, and a coarse 10-stage (Phase 0–9) roadmap. Every later document (07, 09, 10, 11, …) elaborates some section of this one.

**2. Named identifiers defined.**
- *Components:* "Remote Web Gateway" (unprivileged, [01 — Remote Console — Project Master Plan.md](docs/plans/Detailed_Project_Plan/01%20—%20Remote%20Console%20—%20Project%20Master%20Plan.md#L165) / §7 L280); `remote-hostd` (system service, L173/§5.1 L210); "GNOME Session Agent" (user session, L181/§6 L245, lowercase "GNOME session agent" L247, L625); `remote-emergencyd` (L195/§8 L311).

**3. Hard requirements, gates, stop conditions.**
- MUST: same-session only, never a second desktop (§3.1); fail closed — "locked and inconvenient" beats "unlocked and remotely controllable" (§3.2, restated §69); physical display/keyboard/mouse must not expose/control the session while remote KB/mouse must (§3.3); remote authority only via short-lived lease (§3.4); emergency path independent of browser/WebRTC/network/gateway/main daemon/extension/session-agent health (§3.5); TOTP mandatory always, never bypassed by trusted-device status (§9, §13).
- MUST NOT: `remote-hostd` expose `execute(command)` (§5.1); gateway run as root, touch `/dev/input` without proof, directly manipulate Mutter/display config, or hold unrestricted D-Bus access (§7); emergency daemon contain a web server/WebRTC/codec/plugin framework/arbitrary exec (§8); auto-unlock the machine ever (§21, §25); log passwords/TOTP/keys/tokens (§44); store Access Key in `localStorage` (§34); derive Access Key from the Linux password (§12).
- Stop condition: do not spend effort on Internet networking/rendezvous/TURN/polished UI until same-session/virtual-monitor/input-isolation/fail-safe is experimentally validated (§52).
- Production-readiness checklist (§68, ~17 items) and Final Acceptance workflow (§69) gate "production-ready" status.

**4. Technology and library choices.** Entirely language-agnostic — no mention of Rust, TypeScript, Python, or any framework anywhere (confirmed by search). **5. Experiments/tests/procedures.** No individually-IDed experiments (that's Doc 10's job). Hardware Testing (§63: Intel/AMD/NVIDIA × single/multi-monitor/high-DPI/high-refresh/hotplug/sleep-wake). Browser Testing (§64: Chromium/Chrome, Firefox, Safari, Edge, Android, iOS). Emergency Recovery Test wizard procedure (§43) with a 6-line PASS checklist gating "production/unattended mode."
