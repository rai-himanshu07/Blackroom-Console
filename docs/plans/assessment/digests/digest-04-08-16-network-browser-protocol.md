### 04 — Networking & Browser Client Implementation Specification

**1. Purpose & scope**
Defines the networking architecture and browser-client requirements: browser-based remote access over HTTPS/WebSocket/WebRTC, LAN and NAT-traversed connectivity (STUN/TURN/rendezvous/mDNS), dynamic-IP/IPv4/IPv6 handling, host cryptographic identity, browser authentication integration, session establishment/reconnect/disconnect, relay (TURN) architecture, and deployment modes (local/LAN, hosted-gateway, self-hosted). It explicitly must stay compatible with the security spec, cited in-doc as `03_SECURITY_AND_AUTHENTICATION.md` (line 33) — **this underscore-style filename does not match the actual repository file** `03 — Security & Authentication Implementation Specification.md` (em dash, spaces), a broken/inconsistent cross-reference. Core thesis (§2): use the gateway only to *establish* the connection; move interactive desktop traffic to direct WebRTC whenever possible, never invent a custom transport.

**2. Named identifiers defined**
Grouped by kind (all conceptual examples unless noted):

- *Host identity fields*: §16 registration diagram: `host_id`, `public key`, `capabilities`, `connectivity information`; §17 "Host ID": `host_id`, `host_public_key`, `host_private_key` — field-name set differs slightly between the two sections of the same doc.
- *mDNS/Avahi service name* (§25, line 547): `_remote-console._tcp` — explicitly marked "exact service name should be defined during implementation."
- *Input message types* (§45): `keyboard_down`, `keyboard_up`, `pointer_move`, `pointer_button`, `pointer_scroll`.
- *Session identifier*: `session_id` (generic).

**3. Hard requirements, gates and stop conditions**
- MUST NOT build a custom transport ("TCP + custom encryption + custom congestion control", §3).
- MUST NOT send desktop pixels through signalling; MUST NOT send keyboard events through signalling after WebRTC established except for connection management (§11).
- Gateway MUST NOT run as root; MUST NOT have `/dev/input`, unrestricted D-Bus, password DB, TOTP secret, Access Key, or host private key "unless absolutely necessary" (§34).
- MUST NOT use MAC address/hostname/local IP as primary host identity (§16); host private key never leaves host, never logged (§18).
- Rendezvous MUST NOT be the authorization authority (§20–21); host remains source of truth for user/password/TOTP/Access Key/trusted clients/epoch.
- MUST NOT publicly expose username, hostname, internal IPs, session info, resolution, app names, desktop metadata (§23).
- LAN discovery MUST NOT be treated as authentication — "Same Wi-Fi = trusted" explicitly rejected (§25–26).
- MUST validate every message (size, type, version, fields, types, lengths, values, authz state) and MUST NEVER pass network values into shell/file-path/systemd/D-Bus/executable/config contexts (§14).
- Pointer coordinates MUST reject NaN/Infinity/huge/negative-invalid; host's virtual-monitor config is authoritative, not browser-reported dimensions (§46).
- Clipboard and file transfer are explicitly NOT in mandatory v1 scope (§48–49).
- **Central invariant, repeated verbatim multiple times**: `WebRTC connected ≠ Remote session authorized` (§40, §88, §111, §145); browser must not receive desktop content or control capability before authorization completes.
- On connection loss: stop remote input immediately; do not wait indefinitely for WebRTC reconnect while continuing input (§54). Reconnection is always a new authorization event (§55).
- No secrets in URLs/query/fragment/referrer (§39); no sensitive credentials in localStorage/query strings/console logs/analytics/DOM attributes/plain IndexedDB (§38).
- Browser MUST NEVER have an `unlock_host()`-style command (§90); disconnect always means "lock," never "unlock."
- Emergency takeover MUST NOT depend on browser/gateway/WebRTC/Internet/TURN/JavaScript (§91, restated §128).
- Debug mode MUST NEVER auto-disable authentication/TLS/authorization/lease validation/physical safety; no `--disable-auth` shortcuts in production (§131).
- MUST NEVER log password/TOTP/Access Key/session bearer token/private keys/keystrokes/clipboard/desktop contents (§130).
- CSRF protection required on session creation, device registration/revocation, Access Key rotation, TOTP changes, remote-access config, emergency admin APIs (§69); no wildcard CORS on credentialed endpoints (§70); WebSocket must validate Origin + session + protocol version + host/session binding (§71).
- Must not require manual port forwarding/static IP for the standard flow (§76); must remain functional without vendor cloud (§78); TURN must never see plaintext credentials/desktop/keyboard (§30, §129).
- Full 23-item Final Networking Acceptance Criteria checklist (§144) and a 14-item "Do not" list for the Copilot agent (§145) gate completion.

**4. Technology and library choices**
- Frontend (§7, explicitly **suggested, not mandated**): "TypeScript + React or lightweight equivalent + WebRTC APIs + WebSocket + HTTPS." "The exact frontend framework is not mandated." "Do not introduce a heavyweight frontend framework merely because it is popular."
- WebRTC: strongly preferred for the data plane "where practical" (§3, §9) — not literally mandatory, but the doc forbids the alternative (custom transport).
- Codec: explicitly NOT hard-coded — evaluate H.264/VP8/VP9/AV1 based on browser support, hardware acceleration, latency, CPU/GPU, GNOME/PipeWire integration; "capability-driven negotiation preferable" (§42). Hardware acceleration preferred but is "an optimization, not a correctness requirement" (§43).
- TLS: HTTPS mandatory in production, dev may use localhost HTTP (§10); valid TLS certs mandatory in production, self-hosted may use internal CA (§66); certificate pinning explicitly discouraged unless compelling reason (§68).
- mDNS/Avahi suggested for LAN discovery, exact service name TBD (§25).
- TURN: server product unspecified; credentials should be short-lived, never a permanent password embedded in JS (§102).
- No gateway/host-daemon server language or framework is named anywhere in doc 04 (architecture-level only; contrast with Document 00's Rust preference recorded in session memory — doc04 does not repeat or reference that).

**5. Protocol/flow detail**
- **New/untrusted auth flow** (§37): Browser → connect → Gateway → establish signalling → Host → username/password/TOTP/Access Key → Authentication → Session credential → WebRTC.
- **Trusted-device flow** (§38): same path, factors = username + password + TOTP + trusted-client credential; Access Key not required; TOTP still mandatory.
- **16-step canonical remote-session startup** (§110): Browser connects → TLS established → Signalling established → Host identified → User authenticated → Authorization verified → Remote session created → Control lease created → GNOME session prepared → Virtual monitor created → Physical display isolated → Physical input isolated → PipeWire capture established → WebRTC media established → Remote input established → Host enters `REMOTE_ACTIVE`.
- **Clean disconnect** (§112): Browser disconnect → Host revokes lease → Remote input disabled → Remote media stopped → Virtual monitor destroyed → Physical display restored → Physical input restored → GNOME locked.
- **Reconnection** (§55): connection lost → remote control revoked → GNOME locked → physical console restored → new connection → authentication → new remote session (explicitly not an optimized resume by default).
- **Heartbeat** (§53): Browser→`heartbeat`, Host→`heartbeat_ack`, confirming session/auth/epoch/lease all still valid.
- Gateway↔hostd IPC is only referenced at the architecture level here (§34–36, §104–105): narrow, authenticated, versioned; forbids a "generic proxy" (`gateway → RPC(method, arbitrary arguments)`); prefers named ops like `CreateSession`, `Authenticate`, `SignalWebRTC`, `TerminateSession` (§105) — the actual IPC method catalog lives in Document 16 (see there).
- **8-phase implementation order** (§142): Phase 1 local WebSocket prototype (no remote desktop) → Phase 2 authentication → Phase 3 WebRTC connectivity → Phase 4 video (PipeWire→encoder→WebRTC→browser) → Phase 5 remote input (browser→WebRTC→host→libei/GNOME) → Phase 6 control-lease enforcement → Phase 7 failure handling → Phase 8 production infra (rendezvous/STUN/TURN/LAN discovery/self-hosted).

**6. Browser UX detail**
Doc 04 touches UX only lightly (doc 08 owns it): §135 acceptance-test mockups (new-client login form fields: Username/Password/Authenticator Code/Remote Access Key; trusted-device form omits Access Key); §136 status strings ("Connecting…", "Authenticating…", "Starting remote session…", "Connected", "Connection degraded", "Reconnecting…", "Remote session ended", "Host locked"); §137 failure UX principle — show "Unable to establish remote session. The host was returned to its safe local state." not raw ICE/STUN error codes; §138 disconnect confirmation dialog; §139 emergency UX — browser may show "use the configured emergency shortcut on the host," explicitly not the sole recovery path. Keyboard/pointer specifics, fullscreen, accessibility, and trusted-device management screens are *not* detailed here — they belong to doc 08.

**8. Phase/sequencing guidance and definition-of-done**

**11. Risks and feasibility concerns the doc itself raises**
- Browser capability variance across Chromium/Firefox/Safari WebRTC/WebCodecs support (§8–9) — capability-detection gate, no unsafe fallback permitted.

### 08 — Browser / Remote Client UX & Interaction Flow

**1. Purpose & scope**
Defines the complete browser-based remote-client experience: connection discovery, host selection, new-vs-trusted authentication, TOTP, Remote Access Key, session establishment, remote-control activation, connection status/degradation, reconnect/disconnect, emergency-takeover feedback, session expiration, security error messaging, browser security constraints, and client-side state management. Explicit framing (§1–2): the browser is "a remote client, not the authority for workstation security"; the host is source of truth for authentication, authorization, session state, trusted devices, security epoch, control lease, GNOME state, and physical display/input isolation. Product framing: "Connect to my existing Ubuntu workstation securely," not "start another remote desktop session" (§2).

**2. Named identifiers defined**
- *Client state model* (§52, lines ~1089–1098): `DISCONNECTED`, `CONNECTING`, `AUTHENTICATING`, `AUTHENTICATED`, `STARTING_SESSION`, `REMOTE_ACTIVE`, `RECONNECTING`, `DISCONNECTING`, `SESSION_ENDED`, `ERROR`.
- *Session-activation sequence* (§19, lines 444–455) — **a different vocabulary from §52 above, in the same document**: `AUTHENTICATED → AUTHORIZED → PREPARING_REMOTE → DISPLAY_READY → INPUT_READY → REMOTE_ACTIVE`.
- *Browser client events* (§54, lines ~1139–1152): `CONNECT`, `AUTH_SUBMIT`, `AUTH_SUCCESS`, `AUTH_FAILURE`, `SESSION_READY`, `MEDIA_READY`, `CONTROL_READY`, `DISCONNECT`, `NETWORK_LOSS`, `NETWORK_RESTORED`, `SESSION_EXPIRED`, `HOST_TERMINATED`, `EMERGENCY_TERMINATED`, `HOST_UNAVAILABLE`.
- *Error categories* (§55, lines 1160–1183): `AUTH_FAILED`, `AUTH_RATE_LIMITED`, `ACCESS_DENIED`, `HOST_OFFLINE`, `HOST_UNTRUSTED`, `SESSION_EXPIRED`, `SESSION_REVOKED`, `LEASE_EXPIRED`, `HOST_STATE_INVALID`, `GNOME_UNAVAILABLE`, `DISPLAY_SETUP_FAILED`, `INPUT_SETUP_FAILED`, `MEDIA_FAILED`, `NETWORK_FAILED`, `EMERGENCY_TERMINATION`.
- *Connection-status indicator states* (§21): "● Connected", "● Reconnecting", "● Degraded", "● Disconnecting".
- *Performance quality labels* (§59): Excellent, Good, Poor, Reconnecting.
- *Diagnostics panel fields* (§56): Host, Session, Authentication, Control lease, Security epoch, WebRTC, Latency, Packet loss, Video codec, Resolution, PipeWire, GNOME capability.
- *UI copy terms mandated/forbidden*: MUST call it "Remote Access Key" (§12); MUST NOT call it "API key." MUST NOT use color-only status indicators (§57).
- *Screens/blocks* (mockups, no formal names, but effectively screen identities): Initial Connection Screen (§5), Authentication Screen (§8), Trust-this-device dialog (§9), Remote Access Key display (§12), Access-Key rotation dialog (§13), Pre-Remote-Session checklist screen (§18), Remote Desktop View (§20), Disconnect confirmation dialog (§29), Trusted Device Management UI (§49), Active Session Management UI (§50), Revoke-All dialog (§51).
- Every fenced code block carries an `id="xxxxxx"` attribute (e.g. `id="l3jz0r"`, `id="q84d7e"`) — these look like **auto-generated random base36 slugs from an editor plugin**, not meaningful protocol identifiers (contrast with doc 16's semantically-named anchors like `id="lease001"`). Should not be mistaken for wire identifiers.
- No HTTP routes, WS channel names, data-channel labels, storage-key names, ports, or numeric limits are given (consistent with doc 04/16).

**3. Hard requirements, gates and stop conditions**
- Browser is never the security authority; host wins on any state conflict (§53) — example given: browser shows `REMOTE_ACTIVE` while host is `TEARING_DOWN` → browser must transition to `SESSION_ENDED`.
- One active control lease system-wide: only one remote-control browser tab per host (§27, "Another remote session is already active" — no silent stealing) and only one active controller across multiple trusted devices (§28).
- **Trusted-device status must never bypass TOTP** — stated explicitly twice (§9, §62) and reinforced in acceptance criterion C (§63).
- Browser cannot self-declare "I am trusted" — host must validate the credential; absent/invalid credential ⇒ full new-device flow (§11).
- Auth failures must be generic; must never reveal which of username/password/Access Key/TOTP was wrong (§15–16, §63-J).
- Client-side rate-limit timers are UX only; server remains the enforcement point (§17).
- Success/"prepared" state must not be shown until host confirms GNOME session ready + virtual display ready + physical display isolated + physical input isolated (§18); UI must not enter the normal desktop view until `REMOTE_ACTIVE` is confirmed by the authoritative sequence (§19).
- Reconnect permitted only if: session still valid AND security epoch unchanged AND authorization remains valid AND host permits reconnection (§24) — otherwise require new authentication. Browser refresh (§25) and tab close (§26) must never silently restore/retain control; the host lease timeout is the authoritative backstop, not a clean browser disconnect event.
- Revoked-trusted-device UX must fall back to full new-device auth (username/password/TOTP/Remote Access Key) (§33). Unexpected host-identity change must never auto-trust the new identity — requires explicit user verification (§36).
- No secrets in localStorage/URL params/query strings/console logs/analytics events/DOM attributes/plain IndexedDB (§38); no secrets in URL/query/fragment/referrer ever (§39).
- Browser must not implement custom cryptography around WebRTC absent a specific threat model; gateway must not access plaintext media merely by handling signalling (§40); gateway is never authoritative for GNOME state/session authorization/physical input/display/security epoch (§41).
- Clipboard must be independently toggleable and never implicitly assumed safe (§46). Recovery-code flow must not silently bypass TOTP or eliminate the Remote Access Key requirement for a new/untrusted device (§48). Trusted-device secrets must never be displayed in management UI (§49). "Revoke All" must have explicit, enumerated semantics and state clearly whether the Remote Access Key itself is rotated (§51).
- Full 10-item Client Acceptance Criteria A–J (§63) is the acceptance gate: new-device works remotely; trusted-device works; TOTP cannot be bypassed; stale sessions cannot reconnect; disconnect is clear; network loss is safe; browser refresh is safe; host remains authoritative; secrets protected; auth errors leak no info.

**4. Technology and library choices**
Doc 08 is UX-flow-focused and largely defers stack choices to doc 04; it adds: trusted-device key generation should occur "locally in the browser/client environment where technically practical," not transmit a long-term private key through the server (§63-list item under "Trusted Client Registration"); credential storage should use "appropriate browser security mechanisms" — explicitly floats WebCrypto non-exportable `CryptoKey`, platform credential APIs, and WebAuthn/passkeys as *future* candidates, but "must document the chosen mechanism and its security limitations" and must not claim plain localStorage is adequate. WebAuthn/passkeys explicitly **not mandatory for v1** and must not replace the agreed security model "without explicit design review." No frontend framework, build tool, or server language is named.

**5. Protocol/flow detail**
- **First connection (new/untrusted)** (§7): CONNECT → HOST IDENTIFICATION → USERNAME → PASSWORD → TOTP → REMOTE ACCESS KEY → AUTHENTICATE → optionally TRUST DEVICE → REMOTE SESSION.
- **Trust issuance** (§10): host issues cryptographic trusted-device credential → browser stores it securely; credential must be cryptographically random, host-scoped, revocable, device-associated, independent of both the Linux password and the TOTP secret.
- **Pre-session checklist** (§18): "Checking GNOME session ✓ / Preparing virtual display ✓ / Isolating physical display ✓ / Isolating physical input ✓ / Establishing remote connection …" — displayed sequentially before granting the desktop view.
- **Activation sequence** (§19): see identifiers above.
- **Reconnect** (§24): four-condition gate (session valid, epoch unchanged, authorization valid, host permits) else new-auth required.
- **Session-start UX (7 steps)** (§60): open client → select host → authenticate → host prepares workstation → browser receives display → remote input available → session active. Explicitly: user should never need to understand Mutter/PipeWire/libei/systemd/virtual monitors/security epochs.
- **Session-end UX** (§61): normal = Disconnect → host tears down → GNOME locks → physical console restored → "Session Ended" shown; abnormal = connection loss → lease expires → host tears down → GNOME locks → browser eventually shows "Session Ended."
- **20-step implementation order** (§65): basic connection screen → host identity handling → auth UI → TOTP flow → Remote Access Key flow → trusted-device flow → client state machine → session-start progress UI → WebRTC connection → remote viewport → keyboard input → pointer input → connection health → disconnect → reconnect → session-expiration handling → emergency termination handling → trusted-device management → diagnostics → accessibility/polish.

**6. Browser UX detail**
This doc *is* the UX detail; consolidated by topic:
- **Auth screens**: Initial connection screen minimal, optional LAN-discovered host list (§5); host identity is cryptographic, not hostname/IP/MAC (§6); auth form = Username/Password/Authenticator code/Remote Access Key, with the Access Key field hidden for trusted devices (§8); "Trust this device?" checkbox with explicit "TOTP is still required every session" messaging (§9); Remote Access Key shown masked with Copy/Rotate actions and "keep this in your password manager" guidance (§12); rotation requires explicit confirmation and an option to terminate existing sessions (§13); TOTP entry is a plain 6-digit code field, generic failure message (§14–15).
- **Connecting/active states**: pre-session checklist (§18); minimal remote desktop chrome — top bar with connection dot + host name + menu, bottom bar with quality label + Disconnect button, no toolbars covering the desktop (§20); compact status dot states (§21, above).
- **Degraded/interrupted**: "Connection interrupted / Trying to reconnect…" then either "Connection restored" or, if the lease expired, "Remote session ended. The workstation was locked automatically." (§23); explicit non-promise: "Do not promise successful reconnect."
- **Disconnected/revoked/emergency**: explicit Disconnect button + confirm dialog (§29–30); emergency takeover shows "Remote session terminated… taken over locally… must authenticate again," without exposing trigger details (§31); stale-session reconnect shows "This remote session is no longer valid. Please authenticate again." (§32); revoked-trusted-device shows "This device is no longer trusted," falling back to full auth (§33); remote-access-disabled shows a static message with **no repeated reconnect attempts** (§34); host-offline shows "Workstation unavailable," no infra details (§35); host-identity-change shows a hard-stop "identity of this workstation has changed… connection was stopped. Verify the workstation before continuing." (§36).
- **Keyboard handling** (§43): must reproduce normal GNOME keyboard behavior; explicitly acknowledges some browser-reserved shortcuts can't be forwarded; recommends an explicit "Capture keyboard" mechanism; must not claim perfect forwarding where the browser prevents it. IME is not mentioned at all — a gap.
- **Pointer handling** (§44): relative movement (where required), absolute positioning (where appropriate), buttons, wheel, modifiers; cursor sync "must be tested against GNOME/Mutter behavior" (acknowledged uncertainty). Touch/tablet explicitly deferred, "not required for the initial feasibility gate" (§45).
- **Fullscreen/pointer-lock**: not discussed in doc 08 at all (only doc 04 §87 touches "fullscreen," clarifying it is a presentation feature, never a substitute for actual physical-display isolation) — a gap relative to the user's requested coverage.
- **Accessibility** (§57): keyboard navigation, visible focus, readable status messages, screen-reader labels, sufficient contrast, "no color-only security indicators."
- **Trusted-device management UI** (§49): list with Last-used/Status/Revoke per device, plus "Revoke All Devices"; never display secrets.
- **Diagnostics UI** (§56): the field list above; explicitly "safe to copy into bug reports," never secrets.
- **Security messaging rules** (§62, consolidated principle list): never imply auth=control; never imply trusted=passwordless; never bypass TOTP; never auto-trust a new host identity; never expose secrets; never silently reconnect after security-sensitive termination; always clearly indicate session end; prefer generic auth errors; avoid false sense of security.

**7. Tests / verification procedures specified**

Verification is expressed as the lettered **Client Acceptance Criteria A–J** (§63, functions as acceptance tests) and as instruction items 13–14 in §64 ("Add automated tests for authentication and client state transitions"; "Add tests for disconnect, reconnect, revocation, emergency termination, and lease expiration") — no concrete IDs, counts, or matrices are given, unlike doc 16's `ptest001`-style anchors. ### 16 — API, IPC & PROTOCOL SPECIFICATION

**1. Purpose & scope**
Defines the communication contracts across the full chain: Browser ⇄(HTTPS/WebSocket/WebRTC)⇒ Remote Gateway ⇒(authenticated local IPC)⇒ Remote Host Daemon ⇒(authenticated local IPC)⇒ GNOME Session Agent, plus an independent Remote Emergency Daemon ⇒ Host Daemon/GNOME Session safety path. Goal: strict separation of authentication, authorization, session management, control authority, media transport, GNOME operations, privileged operations, and emergency recovery, so that the protocol makes it structurally impossible to confuse "connected" with "authorized to control" (§1).

**2. Named identifiers defined**
This is the richest of the three docs for identifiers; all are conceptual (marked `Conceptually:`/`Example:`) with semantically-named anchor IDs (e.g. `id="lease001"`), not literal wire strings.

**3. Hard requirements, gates and stop conditions**
The document opens with **16 numbered protocol design principles** (§2) that function as the top-level MUSTs: (1) authN/authZ separate, (2) session credentials ≠ login credentials, (3) control authority is temporary, (4) every remote input op requires current authorization, (5) epoch changes invalidate old authority, (6) messages explicitly typed, (7) unknown messages rejected safely, (8) invalid messages never trigger privileged ops, (9) browser state never authoritative, (10) host state authoritative, (11) media transport ≠ control authority, (12) gateway never receives unnecessary secrets, (13) privileged IPC narrow/explicit, (14) no arbitrary command execution, (15) emergency ops independent of browser/network, (16) protocol version changes must never silently weaken security. Additional binding rules:
- Plane D (Local Safety) "must not depend on the Internet" (§3).
- Production requires `HTTPS`/`WSS`/authenticated `DTLS/SRTP`; never plaintext-HTTP production auth (§5, `tls001`); no credentials inside WebRTC data channels (§4, `ext001`).
- TOTP remains mandatory even for trusted devices (§10, `auth002`); auth failures must never reveal which credential component failed (§12); auth requests must not be logged or persisted unnecessarily (§11).
- Control-lease secret must never appear in diagnostics (§17); no valid lease ⇒ `REMOTE INPUT = DENIED` (§18, `lease003`) — this is a repeated, load-bearing invariant.
- IPC callers must be authenticated (UID/peer creds/socket perms/systemd socket activation/D-Bus policy/crypto) — "must not trust a caller merely because it can reach the socket" (§27).
- Safety-critical operations must be idempotent (§34); stale requests must be rejected using transition IDs/request IDs/generation counters/epoch (§36); a timeout must never be interpreted as success — always enter recovery (§37, `timeout001`); partial failure must trigger rollback/recovery, never a silent continuation into `REMOTE_ACTIVE` (§38).
- Media connection never itself grants control (§43); input accepted only while session+epoch+lease+GNOME-input-state are simultaneously valid, else `DROP` — unauthorized input must never be queued for later execution (§44); input requires sequence numbers bound to session/lease, rejecting stale/invalid/replayed data — no replay after reconnect (§45).
- Single-controller policy: default is exactly one active remote controller; a second requester must be explicitly `DENY`ed or given an `EXPLICIT TAKEOVER`, never silently split control (§42).
- No generic `execute_privileged_action(name, args)` may ever be exposed (§65, `priv001`) — only narrow named operations with explicit authorization, bounded arguments, predictable effects, an audit event, and tests (`priv002`).
- Gateway compromise must never automatically yield Linux password, TOTP secret, Remote Access Key, host private key, arbitrary host commands, or unrestricted GNOME control (§66). Browser is untrusted; never rely on browser-side logic for authorization/session validity/lease validity/epoch/safety state (§67) — the browser can *display* `REMOTE_ACTIVE`, but only the host decides if input is actually permitted.
- Never log protocol secrets in the audit trail (§68).
- 27-item Definition of Done checklist (§77) gates protocol-layer completion; **Final Protocol Invariant** (§78) is the capstone rule (quoted in full below).

**4. Technology and library choices**
Doc 16 is deliberately technology-agnostic — it is a contracts spec, not an implementation guide:
- Serialization (§62): "JSON for browser-facing control/signalling" **or** "a binary protocol where performance or strict schemas justify it" — explicitly left as an implementation decision based on browser compatibility, schema validation, security, complexity, and debuggability; "Do not invent an unnecessary custom serialization format."
- Local IPC mechanism (§26): "Unix domain sockets, D-Bus, or another authenticated local IPC mechanism" — selection criteria = required security + GNOME integration; "Do not create a generic IPC proxy."
- No server language, no web framework, no WebRTC library, and no video codec is named anywhere in this document (those choices live in doc 04 and — presumably — doc 03/06, not read in this batch).

**5. Protocol/flow detail**
- **Four communication planes** (§3): Plane A Authentication (username/password/TOTP/Access Key/trusted-device credential) → Plane B Session Control (session creation, authorization, epoch, lease, lifecycle, disconnect, recovery) → Plane C Media/Input (WebRTC media, keyboard, pointer — still gated by the lease) → Plane D Local Safety (emergency trigger, remote revocation, session termination, GNOME locking, display/input restoration; Internet-independent).
- **Session creation** (§14): host verifies authentication session, user authorization, host state, current security epoch, current active-session policy, GNOME availability, and emergency-controller health before issuing a `RemoteSession`.
- **Control lease acquisition/renewal** (§17–19): lease issued after session authorization; renewal requires session-still-exists + client-still-authorized + epoch-unchanged + state-permits-control + not-revoked + connection-healthy, else `RENEWAL = DENIED`.
- **Security epoch** (§20–21): every control-related request carries an epoch; mismatched epoch ⇒ `REJECT`; epoch increments on emergency takeover, revoke-all, security reset, service restart (where appropriate), explicit credential/security reset — "exact event list must be defined by implementation and tested."
- **Emergency contract** (§24–25): `EmergencyTrigger` (source, timestamp) → `REVOKE → EPOCH++ → TERMINATE SESSION → LOCK → RESTORE DISPLAY → RESTORE INPUT → VERIFY` → `EmergencyResult` acknowledgement with explicit per-step booleans; partial success must be representable, not collapsed to a single boolean.
- **Gateway↔hostd IPC method list with authz**: allowed = `authenticate`, `create_session`, `renew_lease`, `disconnect_session`, `get_public_status` (§28) — implicitly all require an authenticated gateway caller (peer-cred/socket-based, §27), but the doc does not state per-method authorization requirements individually (gap — see §10).
- **Hostd↔session-agent IPC method list with authz**: `get_session_state`, `get_capabilities`, `prepare_remote`, `create_virtual_display`, `isolate_physical_display`, `isolate_physical_input`, `start_capture`, `enable_remote_input`, `lock_session`, `teardown_remote`, `restore_display`, `restore_input`, `verify_safe_state` (§29) — each returns an explicit `Result: SUCCESS/FAILED` plus state evidence (§30, e.g. `topology_id=...`); again, no differentiated per-method authz statement beyond "the host daemon is the caller," since this IPC leg is host-daemon-to-agent, not externally reachable.
- **WebRTC signalling**: only addressed at the "media session" ordering level (§43): authenticated → session authorized → control/session policy established → GNOME prepared → WebRTC negotiation → media connected; explicit offer/answer/ICE-candidate message *names* are not given in doc 16 (that granularity lives in doc 04, which is equally abstract — a shared gap).
- **Input events**: format fields not named beyond "sequence number, session ID, lease association" (§45) — no concrete field name like `seq` or `deviceId` is given.
- **Heartbeat/keepalive**: not named explicitly as a message type in doc 16 (doc 04 §53 covers this generically as `heartbeat`/`heartbeat_ack`) — doc 16 only discusses timeout/idempotency abstractly.
- **Disconnect**: `DisconnectRequest{session_id, session_credential}` → `DisconnectResponse{result, final_state}` (§23); host must revoke authority before considering disconnect complete.
- **Reconnect/resume**: `session resume` requires `session_id, session_credential, client_id, security_epoch`, all independently re-verified by host — "Do not trust browser memory of 'I was connected before.'" (§56). Browser refresh triggers "session reconciliation," and duplicate tabs get read-only/denied control unless an explicit transfer flow exists (§57–58).
- **Revocation/emergency notification to browser**: delivered via the `web002` event stream (`CONTROL_REVOKED`, `SESSION_TERMINATED`, `RECOVERY_STARTED/COMPLETE`), consistent with doc 08's UX descriptions.
- **Error handling**: `ErrorResponse{code, category, retryable, user_message, diagnostic_id}` (§52); retry semantics vary by code (`NETWORK_FAILED` retryable=true; `AUTH_INVALID` not retryable until new credentials; `SESSION_REVOKED` not retryable; `DISPLAY_ISOLATION_FAILED` no automatic retry) (§53).

**6. Browser UX detail**
Doc 16 does not own UX (that's doc 08); it only defines the machine-facing contract the UX must consume: the `web001` command set and `web002` event set (above), the fact that browser-visible states must mirror the authoritative state machine's `sess003` list (§15), and the strict rule that the browser may *display* a state but never *decide* one (§67).

**7. Tests / verification procedures specified**
This is the only one of the three docs with concrete test-style anchors:
- `ptest001`–`ptest007` (§70, "Protocol Security Test"): stale session+epoch+lease vs. current host ⇒ `REJECT`; valid session+invalid lease ⇒ remote input rejected; valid auth+unauthorized privileged IPC ⇒ IPC rejected.
- `race001`–`race003` (§71, "Emergency Race Test"): simultaneous input+lease-renewal+network-disconnect+emergency-trigger during `REMOTE_ACTIVE` must still converge on the fully-revoked/locked/restored final state regardless of event ordering.
- `timeout002`–`timeout004` (§72, "Protocol Timeout Test"): GNOME agent stops responding while host awaits display/input prep ⇒ timeout ⇒ no success assumption ⇒ recovery ⇒ safe state.
- §73 "Protocol Restart Test" (unlabeled beyond section number): restart gateway/hostd/GNOME agent mid-operation; verify stale sessions/leases rejected, state reconciled, recovery performed, browser gets a meaningful state/error, no stale input accepted.
- `compat001` (§74, "Protocol Compatibility Test"): same protocol / older compatible client / newer client / unsupported client / unknown message / unknown capability — host must reject unsupported security-sensitive combinations.
- §69 "Protocol Testing": every message type requires tests for valid request, missing fields, invalid types/values, oversized payload, stale session, wrong host/client/epoch, expired credential, unauthorized caller, replay, duplicate request, timeout, concurrent request — a 15-category combinatorial matrix applied per message type.
- §75 "Protocol Documentation Requirements": every message must document name/purpose/sender/receiver/required+optional fields/authN requirement/authZ requirement/state requirements/epoch requirement/lease requirement/expected response/error codes/retry semantics/security implications — a documentation completeness gate, not itself a test, but enforceable as one.
Note: these anchor IDs (`ptest001` etc.) are semantically-named markdown anchors embedded in the spec text, not entries in a separate test-management system — useful as stable citation points but not literal test-runner IDs.

**8. Phase / sequencing guidance and definition-of-done**
§76 gives a 20-item Copilot agent instruction list plus a 13-stage implementation pipeline (`agent02`): `PROTOCOL MODEL → SCHEMAS → VERSION NEGOTIATION → AUTHENTICATION → SESSION → SECURITY EPOCH → CONTROL LEASE → LOCAL IPC → GNOME OPERATIONS → BROWSER CONTROL → WEBRTC SIGNALLING → RECOVERY → RACE TESTING → SECURITY TESTING`. §77's 27-item Definition of Done checklist (protocol versions/capability negotiation/host+client identity/authentication+session+credential contracts/control lease/epoch enforcement/browser protocol/gateway-host IPC/host-GNOME IPC/emergency IPC/message validation/size limits/replay protection/timeout behavior/idempotency/error codes/retry semantics/compatibility tested/stale sessions+leases rejected/race conditions tested/privilege boundaries tested/secrets excluded from logs/emergency network-independence/documentation complete) is the explicit closing gate for this document's scope.

**9. Cross-references**

**10. Ambiguities, gaps, internal contradictions, and conflicts with Document 00**
- **"Create session" has three casings across two documents**: `CreateSession` (§14, line 385, PascalCase) vs. `create_session` (§28 `ipc002`, line ~734, snake_case, gateway→host IPC) vs. `CREATE_SESSION` (§39 `web001`, line 1010, SCREAMING_SNAKE_CASE, browser-facing) — compounding doc 04's own three-way variance on the same term (§12/§15/§105 there).

- §28's Gateway→Host IPC list has **no explicit per-operation authorization requirement** stated (the user's request specifically asked for "IPC method lists... with authz requirements" — doc16 states generic caller-authentication requirements (§27) but does not enumerate, e.g., "`authenticate` requires no prior session; `renew_lease` requires an existing valid session+epoch" as a table). This must be inferred from surrounding prose (§19 renewal checks, §14 session-creation checks) rather than stated per-method — a documentation gap relative to the request.
- No conflicts found with Document 00's component names or its "browser never authoritative" framing — doc16 is fully consistent with Document 00 on those points, and is in fact the strongest reinforcement of Document 00's authority model of the three documents in this batch.

**11. Risks and feasibility concerns the doc itself raises**
- §21 explicitly defers the definitive list of epoch-incrementing events to "implementation and tested" — acknowledging the spec itself is incomplete on a security-critical trigger list.

- §74 (compatibility test) acknowledges protocol version skew between client/host as an ongoing operational risk once the system is deployed to more than one host/browser version simultaneously.
- The sheer combinatorial size of §69's per-message-type test matrix (15 categories × every message type) is self-acknowledged as large ("every message type requires tests for...") — a testing-effort risk the document surfaces without resourcing it.

3. **"Create session" triple-casing** — `"create_session"` (04§12, line 288) / `create_session`/`create_session_result` (04§15, lines 354/361) / `CreateSession` (04§105, line 2043; 16§14, line 385) / `create_session` (16§28 `ipc002`, line ~734) / `CREATE_SESSION` (16§39 `web001`, line 1010).
4. **"Renew" naming split** — `renew_lease` (16§28 `ipc002`, gateway→host IPC) vs. `RENEW_CONTROL` (16§39 `web001`, browser protocol) — different root word, not reconciled; more broadly, four of the nine `web001` browser commands (`REQUEST_CONTROL`, `RELEASE_CONTROL`, `GET_SESSION_STATUS`, `GET_CAPABILITIES`) have no matching entry at all in the five-item `ipc002` gateway→host list.
5. **Host-identity field names** — 04§17 (`host_id, host_public_key, host_private_key`) vs. 04§16 (`host_id, public key, capabilities, connectivity information`) vs. 16§6 `host001` (`host_id, public_key, fingerprint`) — three slightly different field sets for the same concept, none reconciled.
6. **Cross-reference style inconsistency** — 04§1 (line 33) is the *only* one of the three docs to cite another spec document by name, and it cites the wrong filename form (`03_SECURITY_AND_AUTHENTICATION.md` vs. the actual `03 — Security & Authentication Implementation Specification.md`); docs 08 and 16 cite no documents by name/number at all, despite depending heavily on doc 03's TOTP/epoch/lease model and doc 07's state machine.
7. **Documentation-tooling artifact, not a true contradiction but worth flagging**: doc 08's fenced-block `id="..."` values are random-looking base36 strings (e.g. `l3jz0r`), while doc 16's are meaningful topic-coded slugs (e.g. `lease001`, `ptest003`) — inconsistent authoring convention that could mislead an implementer into treating doc 08's IDs as meaningful.

**The 5 most decision-relevant insights for implementing gateway, protocol, browser client and WebRTC phases**
1. **Adopt Document 16's `sess003` list as canonical immediately and write a mapping table** before writing any code — the four divergent state vocabularies (above) are the single biggest risk of building inconsistent gateway/host/browser state machines that talk past each other. Do this before Phase 2 of doc 04's implementation order.
2. **The gateway must expose only a closed, named set of operations to the host — never a generic RPC** — reiterated independently in 04§105 ("No Generic Proxy"), 16§28/§65 (`ipc002`/`ipc003`, `priv001`/`priv002`), and 16's design principle #14. This is the most heavily cross-reinforced architectural rule in the whole batch and should be treated as non-negotiable for the gateway's IPC client code.
3. **`WebRTC connected ≠ authorized ≠ REMOTE_ACTIVE` is the single most repeated invariant across all three documents** (04§40/§88/§111/§145; 08§19/§53; 16§43/§67/§78's Final Protocol Invariant) — the browser/gateway must never be allowed to short-circuit the full chain (auth → authz → session → epoch → lease → GNOME-prepared → physical-isolation-confirmed → media-ready) to reach an active-looking UI state. This should be enforced as a single server-side gate function, not scattered checks.
4. **Reconcile the browser-facing protocol (`web001`/`web002`, 16§39–40) against the gateway→host IPC surface (`ipc002`, 16§28) before building the gateway** — four browser commands currently have no defined backing IPC call (Contradiction #4 above); this must be resolved (either by extending `ipc002` or by explaining why the gateway can serve those calls without hostd) before gateway implementation starts, or the gateway will end up inventing ad hoc calls that violate principle #14.
5. **Neither doc numerically specifies timeouts, message-size limits, ports, or codec/ICE config** — every "timeout"/"limit" section in docs 04 and 16 is a bare category list with no numbers (04§107–109; 16§37/§61). These values must be decided and documented as a first implementation artifact (a shared constants/config module) rather than invented ad hoc per component, since three different subsystems (gateway, hostd, browser) all need matching values (e.g., heartbeat interval, lease TTL, auth-session TTL) to avoid divergent behavior.
