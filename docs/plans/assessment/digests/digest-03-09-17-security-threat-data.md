### 03 — Security & Authentication Implementation Specification

**1. Purpose & scope**
Doc 03 ([03 — Security & Authentication Implementation Specification.md](docs/plans/Detailed_Project_Plan/03%20—%20Security%20&%20Authentication%20Implementation%20Specification.md)) is the normative authentication/authorization architecture for the whole product: PAM-backed Linux login, mandatory TOTP, the Remote Access Key, trusted-client credentials, session credentials, control leases, the security epoch, revocation, emergency takeover, secret storage, rate limiting, capability-based authorization, security logging, and recovery (lines 1–32). It explicitly states normative force: "This document is normative for the implementation. If another design conflicts with this document, do not silently choose one. Document the conflict and resolve it explicitly." (~lines 28–32). The stated security objective (§2, lines 34–46): *"A remote failure, expired credential, compromised client session, or ambiguous system state must never leave the workstation both unlocked and remotely controllable"* — the system must fail closed.

**2. Named identifiers defined**
*Credentials/tokens:* Linux username, Linux password, TOTP code (§3, 48–91); **Remote Access Key** (§15–18, 355–432; explicitly NOT to be called "API key" in the UI — line 381); trusted-client credential (§19–23); session credential (§24–26); recovery codes (§57–59, 1231–1298); host_id / host_private_key / host_public_key (§52, 1130–1151); client_id / client_public_key (§53, 1152–1166).
*Structs/records:* `TrustedClient` (§19, 433–457): `client_id, public_key, credential metadata, created_at, last_used_at, status`. `ControlLease` (§28, lines 646–667): `session_id, host_id, user_id, client_id, security_epoch, issued_at, expires_at, capabilities`. `SecretStore` abstraction (§54, 1167–1186) conceptually holding: host identity, TOTP secret, Remote Access Key verifier, trusted client credentials, revocation metadata.
*IPC message names* (§74, 1554–1586): `AuthenticateRequest/AuthenticateResult, CreateRemoteSession/RemoteSessionCreated, AcquireControlLease/LeaseGranted, RenewControlLease/LeaseRenewed, RevokeLease/LeaseRevoked, EmergencyTakeover/EmergencyCompleted, RestorePhysicalConsole/PhysicalConsoleRestored`.
*Protocol operations* (§37, 821–847): `send_keyboard_event, send_pointer_event, request_control, release_control, start_remote_session, stop_remote_session`.
*Capabilities* (§35, 786–807): v1 = `VIEW, CONTROL`; future = `CLIPBOARD, FILES, POWER, SETTINGS`.
*Security event names* (§61, 1324–1354): `AUTH_SUCCESS, AUTH_FAILURE, PASSWORD_FAILURE, TOTP_FAILURE, ACCESS_KEY_FAILURE, CLIENT_REGISTERED, CLIENT_REVOKED, SESSION_CREATED, SESSION_TERMINATED, LEASE_CREATED, LEASE_EXPIRED, LEASE_REVOKED, ACCESS_KEY_ROTATED, TOTP_CHANGED, REMOTE_ACCESS_ENABLED, REMOTE_ACCESS_DISABLED, EMERGENCY_TAKEOVER, SECURITY_EPOCH_CHANGED`.
*Security epoch:* `security_epoch` integer, example transition 17→18 (§31–32, 715–749).
*Sizes/encodings:* Remote Access Key `>= 256 bits of entropy` (line 368), encoded `Base64url` (line 371) — the only concrete numeric security parameter in the entire document.
*Everything else is explicitly unspecified*: no clock-skew number ("small acceptable... window appropriate for TOTP... Document the chosen window," line 318), no TTL numbers (only "short-lived," "document the default," e.g. §69 line ~1481), no rate-limit numbers (§40–41, 891–926, only dimensions: IP / host-device / account / client identity), no lockout thresholds, no file paths/UIDs/permission-modes anywhere in the document (confirmed absent by search). Doc paths named at §107 (2269–2286): `docs/security/architecture.md, threat-model.md, authentication.md, credential-lifecycle.md, incident-response.md, security-testing.md`, plus `docs/security/threat-model.md` at §99 (~2049) — these are documentation locations, not runtime storage paths. No P0/P1 severity tags or T-xxx threat IDs exist anywhere in this document; §119 (2562) is merely called "a hard production gate" in prose.

**3. Hard requirements, gates and stop conditions**
MUST/NEVER items are dense throughout: §5 forbids deriving credentials from each other (Access Key ≠ hash(user+pass); TOTP secret ≠ derived from password; client credential ≠ derived from Access Key). §7 — never log/persist/cache the Linux password, never send it to the GNOME agent, never over WebRTC, never in the session DB/URLs/browser storage/error messages/crash reports. §17 — Access Key must never be logged, in URLs, cookies, localStorage, a status API response, sent to the GNOME agent, or exposed to WebRTC data plane. §36 — only `CONTROL` capability + valid lease may send keyboard/pointer/scroll input; `VIEW` clients must never send input. §37 — never expose a generic `execute(command)`. §38 — only one controller at a time in v1; default REJECT on contention. §76 — fail-closed default: authorization-uncertain ⇒ deny. §77 — never enter `REMOTE_ACTIVE` unless physical display isolation is confirmed. §80 — recovery operations (`revoke_remote_session, restore_physical_console, lock_session, increment_epoch, disable_remote_input`) must be idempotent. §82 — epoch persistence must prevent rollback. §102–104 — no custom crypto; CSPRNG only for all security-sensitive randomness (Access Key, session IDs, nonces, client credentials, recovery codes, host keys); never `rand()`/timestamps/UUIDs-as-secrets. §124 final "Do not" list: never weaken mandatory TOTP, never let trusted clients bypass TOTP, never make device pairing mandatory for all access, never store Linux passwords, never expose secrets to browser/GNOME agent unnecessarily, no custom crypto, no arbitrary remote command execution, never run the whole app as root, never silently change security semantics for convenience.

**4. Technology and library choices**
Notably abstract — properties are mandated, specific libraries are not. **PAM**: "Use Linux PAM for system-account authentication. The application should not create a second Linux password database" (§6, 144–170), but "Research the correct Ubuntu 26.04 PAM integration before implementation. Do not assume PAM behavior from older Ubuntu releases" — no PAM crate/binding named. **TOTP**: "Use standard TOTP," compatible with Google Authenticator/Microsoft Authenticator/Authy/Aegis/Bitwarden/1Password (§9, 221–240) — no crate named, and doc03 itself never cites RFC 6238 (that citation only appears in doc09). **Hash/KDF/MAC/signature**: zero mentions of argon2, bcrypt, scrypt, PBKDF2, HMAC, Ed25519, or X25519 anywhere (confirmed via search) — entirely deferred. **Secret storage**: options listed, none mandated — "root-only filesystem permissions... OS keyring/secret service where appropriate... encryption at rest... secure backup behavior" (§11, 283–307). **Transport**: "HTTPS/WebSocket + WebRTC" mandated at the protocol-family level (§49, 1081–1102); "Do not implement custom cryptography... Do not invent a custom encryption protocol." **Rust crates**: none named; only tooling named is `cargo audit` (line 2352, §110). This pattern — mandate the property, defer the library — is consistent across all three documents (see Cross-document notes).

**5. Authentication & authorization flow detail**
*New/untrusted device* (§20, 458–493): browser supplies username+password+TOTP+Remote Access Key → on success, host offers "Trust this device?" → No = temporary session, Yes = register client credential. Explicitly: "Physical access to the Ubuntu host is not required. This is critical." *Trusted device* (§21, 494–521): client credential + username + password + TOTP; Access Key not required; TOTP still mandatory — explicitly rejects "trusted client → credential only → access." *Unknown-device recovery while away* (§22, 522–548) repeats the new-device flow with no physical interaction, "must work through the rendezvous/network architecture." *TOTP enrollment* (§10, 241–282): setup UI shows "NOT CONFIGURED" → generate secret → display QR → user scans, enters current code → server verifies → only then "TOTP: CONFIGURED." *Access Key generation/rotation* (§15–18, 355–432): auto-generated (never user-created), ≥256-bit CSPRNG, Base64url; `[Rotate Remote Access Key]` invalidates prior key for new/untrusted clients only (trusted clients unaffected unless explicitly revoked); separate stronger op `[Rotate Key + Revoke All Clients]` (line 426) for full reset. *Trusted-device enrollment/revocation* (§19,23, 433–457, 549–572): revocation must (1) prevent new sessions with that credential, (2) invalidate active sessions, (3) invalidate its lease, (4) remove/disable authorization state. *Session credential issuance* (§24–26, 573–624): issued only after full authentication succeeds; must be unpredictable/short-lived/revocable/bound to host+user+client+session+epoch/capability-limited; never store permanent secrets in URL/localStorage/plaintext IndexedDB/logs. *Lease issuance/renewal/revocation* (§28–30, 646–714): `ControlLease{session_id, host_id, user_id, client_id, security_epoch, issued_at, expires_at, capabilities}`; heartbeat renews; heartbeat failure → lease expires → input disabled; the application-level lease is explicitly "an additional safety boundary" beyond transport state. *Epoch increment triggers* (§31–33, 43, 46, 96): explicitly stated for Emergency Takeover (§43, line 944), Remote Access Disable (§46, line 1003), and Revoke All Sessions (§96, line 1995) — but §47 Credential Changes (1022–1067, covering password change / TOTP change-reset / Access-Key rotation / trusted-client revocation) does **not** list epoch increment for any of those four cases. *PAM helper design* (§8, 192–220): conceptual chain `remote-hostd → authenticated local IPC → PAM authentication helper → PAM`; explicitly hedged — "The exact architecture may differ after research" — minimize privileges/lifetime/API surface, never expose PAM to network directly. *Lockout/rate limiting* (§40–41, 891–926): rate-limit password/TOTP/Access-Key/device-registration/session-establishment attempts using "increasing delays or other appropriate protection," across IP + host/device + account + client identity dimensions, with no numeric values given, and an explicit caution against permanently locking out legitimate users. *Clock skew* (§83, 1756–1772): "document acceptable clock skew... behavior when system clock changes significantly... during suspend/resume... when NTP adjusts time... Do not silently broaden TOTP validity to compensate." *Browser storage* (§26, §63): no permanent secrets in URL/query string/localStorage/plaintext IndexedDB/logs; short-lived state via secure cookies or equivalent. *Gateway visibility* (§50, §55, §73): gateway must never receive password/TOTP/TOTP-secret/Access-Key/private-keys/pixels/keystrokes/clipboard; gateway has "no access to secrets" architecturally; D-Bus access from gateway to hostd must be a narrow authenticated IPC, not generic D-Bus forwarding.

**6. Threat model detail (doc 03's own subset)**
Doc03 embeds its own compact threat model at §99–101 (2045–2169), independent of and overlapping doc09: attacker-knows-host-IP → cannot authenticate; attacker-knows-username → still needs password+TOTP; knows username+password → still needs TOTP; knows Access Key → still needs username+password+TOTP; steals trusted-client credential → TOTP still required; compromises TURN → cannot decrypt desktop; obtains active session token → limited by expiry/revocation/lease/epoch; physical attacker → analyzed separately; triggers emergency shortcut → remote access revoked, machine locked, physical console restored. §100 explicitly limits scope: application-level controls give no guarantees against root/kernel/firmware/physical-disk compromise; the emergency mechanism targets "remote software failure, stuck remote connection, accidental remote state, unwanted remote control, local user takeover" — not a physical-security system. §101 flags supply-chain hardening (signed releases, authenticated update metadata, SBOM, rollback protection) as future work: "Do not build an automatic self-updater before its security model is defined."

**7. Data model detail**
Doc03 touches storage lightly, deferring to doc17: §54 `SecretStore` abstraction; §81 Security State Persistence (1710–1731) — persist host identity, TOTP configuration, Access Key verifier, trusted clients, security epoch, relevant configuration; never persist passwords, active keyboard input, screen data, unnecessary session secrets; §82 epoch persistence must resist rollback across restart.

**8. Tests / verification procedures specified**
§108 Security Testing (2287–2330) groups: Authentication (correct creds, wrong password/TOTP/Access-Key, expired TOTP, revoked client, rotated key, invalid/expired session), Authorization (view-only can't control, unauthorized can't create lease, expired lease/old epoch can't send input, revoked client can't reconnect), Revocation (session/device/all, emergency, key rotation), Failure (gateway/hostd/agent crash, network failure, browser failure, PipeWire failure, emergency operation). §109 Fuzzing targets (2331–2346): auth protocol parsing, WebSocket messages, WebRTC signalling, IPC messages, remote input messages, config parsing, serialized session/lease structures — "Never fuzz against a production system." §112 pre-release checklist (18 items, 2391–2421). §113–121 nine **Security Acceptance Tests** (2422–2630), the closest thing to test IDs (named by section number/title): §113 Trusted Device (Access Key not required, granted), §114 New Device (Access Key required, granted), §115 Wrong TOTP (denied even for trusted client — "trusted-client credential must not bypass TOTP"), §116 Wrong Access Key (denied), §117 Revocation (active session terminated, lease revoked, future auth denied), §118 Emergency (input revoked, session terminated, epoch incremented, GNOME locked, display/input restored, old session can't reconnect), §119 Emergency With Main Daemon Failure ("This is a hard production gate"), §120 Old Lease after epoch bump (REJECT), §121 Different Laptop While Physically Away (no physical interaction with host — "mandatory product requirement").

**9. Phase / sequencing guidance and definition-of-done**
§123 Implementation Order (2684–2751), 15 sequential steps: (1) security data structures, (2) host identity, (3) secure secret storage, (4) PAM authentication, (5) TOTP setup/verification, (6) Access Key generation/storage/rotation, (7) authentication state machine, (8) trusted client credentials, (9) session credentials, (10) security epoch, (11) control leases, (12) authorization integration with remote input, (13) revocation, (14) emergency takeover integration, (15) failure-path testing — "Only after these are working should they be connected to the production WebRTC/browser layer." §124 (2752–2837) mandates pre-coding research (repo inspection, `adaptive-workflow-configurator` workflow inspection, existing architecture, current Ubuntu 26.04/PAM/GNOME 50 research, dependency identification, decision documentation) before any implementation.

**10. Cross-references**
References `adaptive-workflow-configurator` (§124, ~2755), `docs/security/*` documentation set (§107), an implied GNOME PoC validation dependency for lease-expiration cleanup ordering (§30, line ~713, "must be validated against the GNOME PoC" → doc02/doc10), and its own embedded threat-model subset that duplicates doc09.

**11. Ambiguities, gaps, internal contradictions**
(a) `ControlLease` fields (line 646–667: `session_id, host_id, user_id, client_id, security_epoch, issued_at, expires_at, capabilities`) name the user field `user_id`, while the user-supplied doc00 summary states the tuple as `(host_id,user,client_id,session_id,security_epoch,issued_at,expires_at,capabilities)` — a `user` vs `user_id` naming variance to reconcile against actual doc00 text. (b) Doc03's own §99–101 threat model (2045–2169) duplicates doc09's much larger treatment without cross-reference by section number — a drift risk if one is updated and not the other. (c) Epoch-increment triggers are incompletely enumerated: unconditional for Emergency (§43/944), Disable (§46/1003), Revoke-All (§96/1995), but **absent** from §47 Credential Changes (1022–1067) for password change, TOTP reset, Access-Key rotation, and single trusted-client revocation — leaving whether those four events bump the epoch genuinely undefined within this document (see Cross-document notes for the 3-way inconsistency this compounds into). (d) §16 (line 381) "Do not call it an API key in the primary user interface" constrains UI wording only, leaving internal code/log/API field naming unaddressed. (e) §8 PAM helper architecture is explicitly hedged ("may differ after research") — a genuinely open design question, not a contradiction, but a stated gap. (f) Doc03 never cites RFC 6238 by number even though it is the "normative" authentication document; only doc09 does (line 522) — an internal rigor asymmetry between the two security docs.

**12. Risks and feasibility concerns the doc itself raises**
§30 lease-expiration cleanup order "must be validated against the GNOME PoC" (unproven). §70–71 daemon-failure recovery design is asserted as a requirement but the concrete mechanism ("systemd supervision... watchdog... independent emergency controller") is left open. §77 acknowledges GNOME may not reliably confirm display isolation, forcing an unresolved fail-closed branch. §83 flags clock/NTP/suspend-resume TOTP edge cases as unresolved documentation debt. §100 explicitly disclaims guarantees against root/kernel/firmware/physical-disk compromise. §101 explicitly defers all supply-chain hardening (signed releases, SBOM, rollback protection) as future work, not a v1 prerequisite. §119 flags "emergency during main-daemon failure" as "a hard production gate," i.e., a not-yet-proven, high-risk integration point.

### 09 — Threat Model, Security Boundaries & Abuse Cases

**1. Purpose & scope**
Doc09 ([09 — Threat Model, Security Boundaries & Abuse Cases.md](docs/plans/Detailed_Project_Plan/09%20—%20Threat%20Model,%20Security%20Boundaries%20&%20Abuse%20Cases.md)) is the adversarial contract: security objectives, assets, trust boundaries, attacker capabilities, per-category threats, abuse cases, security invariants, and test requirements, explicitly "intended to guide implementation, code review, penetration testing, and release acceptance" (~line 20). Objective (§2, 34–65): allow authorized remote control of the existing GNOME session while ensuring loss/theft/interruption/compromise of connectivity can never silently leave the workstation under unauthorized remote control; twin goals of confidentiality (no unauthorized viewing/clipboard/activity access) and integrity (no unauthorized input injection, no authority persistence past termination/emergency).

**2. Named identifiers defined**
*Assets* (§4, 94–201), a clean 10-item numbered scheme: 4.1 User Credentials (Linux username/password, TOTP secret, recovery codes), 4.2 Remote Access Key, 4.3 Trusted-Device Credentials, 4.4 Session Credentials, 4.5 Control Lease, 4.6 Security Epoch, 4.7 GNOME Session, 4.8 Physical Display, 4.9 Physical Input, 4.10 Host Identity.
*Attacker classes* (§11, 367–446), lettered A–J: A. Internet attacker, B. LAN attacker, C. Credential attacker, D. Stolen-device attacker, E. Stolen-Remote-Access-Key attacker, F. Malicious local user, G. Compromised browser, H. Compromised gateway, I. Malicious authenticated user, J. Faulty software.
*Trust-boundary components* (§5–10, 202–366): Browser Client (untrusted network) → Remote Gateway (unprivileged) → `remote-hostd` (privileged) → GNOME Agent (user session) → Mutter/PipeWire-libei; separate independent Emergency path: Physical keyboard → `remote-emergencyd` → revoke/lock/restore-display/restore-input.
*Abuse cases* (§81–98, 1685–1905), 18 total, identified only by section number + descriptive title (no T-xxx scheme): §81 Remote Input Without Authentication→DENY; §82 Correct Password, Wrong TOTP→DENY; §83 Correct Password+TOTP, Wrong Access Key→DENY; §84 Trusted Credential Without TOTP→DENY; §85 Stale Session After Emergency→DENY (epoch changed); §86 Reconnect During Teardown→DENY; §87 Gateway Attempts Privileged Command→DENY; §88 Malformed IPC→reject+log+stay alive; §89 Flood Authentication Endpoint→rate-limited; §90 Flood WebRTC Sessions→limits/quotas/authz; §91 Malicious Browser Origin→reject; §92 Host Identity Changed→warn/stop/require verification; §93 Main Daemon Crash→lease expires/input revoked/session locked/hardware restored; §94 Emergency During Main-Daemon Crash→emergency still works; §95 Physical Display Restoration Failure→FAILED_SAFE if uncertain; §96 Physical Input Restoration Failure→FAILED_SAFE; §97 Power Loss During Remote Mode→old sessions invalid, safe local state; §98 GNOME Session Logout→terminate remote session, no cross-session attach.
*Security Test Matrix* (§99, 1906–1940): 24-row table (No credentials/Wrong password/Wrong TOTP/Wrong Access Key/Trusted without TOTP/Revoked device/Expired session/Expired lease/Old epoch/Emergency takeover/Reconnect after emergency/Browser refresh/Network loss/Gateway crash/Host daemon crash/GNOME agent crash/Mutter failure/Display restore failure/Input restore failure/Power loss/Monitor hotplug/Malformed IPC/Auth flood/WebSocket flood/Unauthorized D-Bus/Gateway command-execution attempt) each mapped to an expected result.
*Hard Security Gates* (§100, 1941–1986), lettered A–J, called "release blockers": A Authentication, B TOTP (cannot be bypassed for trusted clients), C Session Isolation, D Lease Expiration, E Security Epoch, F Physical Input Isolation, G Physical Display Isolation, H Emergency Independence, I Safe Teardown, J No Arbitrary Privileged Execution.
*Correlation fields* (§74, 1543–1560): `host_id, session_id, client_id, transition_id, security_epoch`.
*Systemd directives* (§78, 1608–1633): `NoNewPrivileges, PrivateTmp, ProtectSystem, ProtectHome, RestrictAddressFamilies, RestrictNamespaces, RestrictSUIDSGID, CapabilityBoundingSet, DeviceAllow, MemoryMax, TasksMax`.
*Forbidden capabilities* (§79, 1634–1655): `CAP_SYS_ADMIN, CAP_SYS_PTRACE, CAP_NET_ADMIN`.
*Algorithm named:* RFC 6238 TOTP (line 522) — the only RFC citation across all three documents.
*Concrete UI timing value:* "specific key combination + approximately 2-second hold" for the emergency shortcut (§30, line 830) — immediately qualified as "should be configurable."
Note: heading anchors like `id="q7j4m2"` scattered through fenced code blocks are auto-generated markdown slugs, not a semantic threat-ID scheme — no T-xxx identifiers exist anywhere in this document.

**3. Hard requirements, gates and stop conditions**
§75 Secret-Handling Rules (1561–1578): never log/expose Linux password, TOTP secret, TOTP recovery codes, Remote Access Key, trusted-device private credential, session bearer credential, control lease token — "Even debug builds should avoid printing them." §36 Credential Storage minimums (923–946). Gates A–J (§100) are explicit release blockers. §101 vs §102 (1987–2021): a clean accepted-risk/not-accepted split (see §6 below). §33–35 forbid generic privilege escalation surfaces: `execute(command), run_as_root(command), dbus_proxy(method,...), shell(...)` must never be exposed to browser/gateway/GNOME agent. §79 forbids granting powerful capabilities "unless demonstrably required," and if unavoidable requires isolation/documentation/scope-testing.

**4. Technology and library choices**
RFC 6238 TOTP is mandated by name (line 522) with an explicit prohibition: "Do not build vendor-specific Google/Microsoft authenticator integration." §76 Dependency Security (1579–1593) says only "prefer mature cryptographic libraries" — no library named. §78 names concrete systemd sandboxing *directives* (not libraries). TLS is assumed throughout (§47 Man-in-the-Middle, 1099–1114) but no TLS library (rustls/openssl) is named. No hash/KDF/signature algorithm named anywhere in this document either (confirmed by search) — same abstraction pattern as doc03.

**5. Authentication & authorization flow detail**
Doc09 restates the three-tier contract as threat-model framing rather than flow detail (§12, 447–486): normal = username+password+TOTP; new/untrusted = +Remote Access Key; trusted = +trusted-device credential — "No single credential should be sufficient for remote control." It then frames each factor adversarially: Password attacks/mitigations (§13, 487–510: brute force/credential stuffing/spraying/leaked/reused → PAM+rate-limit+generic-errors+audit+TOTP+AccessKey); TOTP attacks (§14–15, 511–542: brute force/replay/stolen-secret/phishing → standard RFC6238+server validation+rate-limit+clock-skew window+no secret exposure); Remote Access Key threat (§16, 543–560: possession alone insufficient, still needs user+pass+TOTP for new device); Trusted-device theft (§17–18, 561–593: stolen device still needs user+pass+TOTP; individual revocation must invalidate future auth + associated active sessions); Revoke-All (§19, 594–614: terminate sessions + invalidate trusted-device credentials + epoch increment "recommended"); Session hijacking (§20, 615–635: mitigated by TLS+short-lived credentials+leases+epoch+host-side authz+no-URL-credentials); Control-lease theft (§21, 636–651: lease "must include session ID, client ID, security epoch, expiration, capabilities" — no host_id/user field listed); Replay (§22, 652–675: mitigated by TLS+server-side session state+nonces+expiration+epoch+unique IDs); Epoch attack (§23, 676–693: old session must be rejected once `epoch_old != epoch_current`); Emergency race (§24, 694–715: emergency has strict priority over normal input, no new input accepted once emergency starts); Reconnect race (§25, 716–743: stale reconnect during TEARING_DOWN must be rejected, no simultaneous teardown+reactivation of the same session).

**6. Threat model detail**
Full trust-boundary chain (§5, 202–261) plus a separate, network-independent emergency path (§5, 245–260). Ten assets (§4) and ten attacker classes (A–J, §11) as listed in §2 above. Systematic threat coverage by category: Authentication (§12–19), Session/Lease/Replay/Epoch/Race (§20–25), Display privacy (§26–27), Physical input (§28–29), Emergency shortcut (§30–32), Privilege escalation/D-Bus/filesystem (§33–36), Browser (XSS §38, CSRF §39, Clickjacking §40), Network (WebSocket §41, WebRTC §42, TURN §43, Rendezvous §44, DNS §45, LAN/mDNS §46, MITM §47), Denial of Service (§48), Enumeration (Auth §49, Session §50, Host §51), Information leakage (§52), Malicious authenticated user (§53), Clipboard exfiltration (§54, recommends leaving clipboard disabled until core system is secure), File transfer (§55, explicitly out of scope — "significantly expands the attack surface... Do not add it merely because remote-desktop products commonly provide it"), Browser extension/stolen profile (§56–57), Stolen Access Key (§58), Lost authenticator/lost Access Key (§59–60), Emergency-after-credential-theft / emergency-after-daemon-compromise (§61–62), Compromised GNOME agent/gateway/host (§63–65 — §65: "This system cannot provide meaningful security guarantees" if the OS/kernel is compromised — assumption explicitly documented), Physical attacker (§66 — outside complete protection boundary; not a physical-security system), Lock-screen/notifications/display confidentiality (§67–69), Session confusion / session-confusion-after-logout / multi-user safety (§70–72 — must verify target user/UID/session-ID/Wayland display/seat/Mutter instance before activation; never "blindly select the first available session"). Then abuse cases §81–98 and Gates A–J (§100) as in §2. §101 **Threats Explicitly Accepted** (1987–2002): fully compromised kernel, malicious root user, physically destructive attacks, compromised physical hardware, compromised authenticator device, fully compromised client OS, availability loss from powerful network attackers. §102 **Threats Not Accepted** (2003–2021): remote input without valid auth, trusted-device TOTP bypass, stale-session reuse after revocation/emergency, indefinite control after network loss, arbitrary privileged execution, unauthenticated GNOME access, silent wrong-session attachment, automatic unlock after disconnect, network-dependent emergency, exposed physical display/input where isolation is claimed.

**7. Data model detail**
Doc09 only lightly touches storage, deferring to doc17: §36 Credential Storage (password→PAM; TOTP secret→protected local storage; Access Key→preferably verifier/hash; trusted-device creds→protected credential storage — "Never store secrets in application logs"); §73–74 Security Logging/Audit Correlation fields (`host_id, session_id, client_id, transition_id, security_epoch`).

**8. Tests / verification procedures specified**
§99 Security Test Matrix (24 rows, 1906–1940). §103 Security Review Checklist (18 yes/no questions, 2022–2050, e.g. "Can an old browser session reconnect after emergency? Can the wrong GNOME session be selected? Can the system ever automatically unlock?" — "Every answer must be demonstrable from code and tests."). Gates A–J (§100) double as acceptance criteria.

**9. Phase / sequencing guidance and definition-of-done**
§104 Implementation Instructions for GitHub Copilot Agent (14 numbered principles, 2051–2071): inspect repo → inspect `adaptive-workflow-configurator` workflow → respect it → treat this doc as the adversarial contract → implement security boundaries before convenience features → keep privileged code minimal → keep emergency path independent → no generic privileged RPC → no custom crypto → use established TLS/PAM mechanisms → add negative/security tests before declaring features complete → add failure-injection tests for every critical transition → never weaken an invariant to pass a test → stop and report if a requirement can't be safely implemented. No explicit "Definition of Done" checklist section exists in doc09 (unlike doc17's §76) — an asymmetry worth noting.

**10. Cross-references**
References `adaptive-workflow-configurator` (§104, ~2053); implicitly depends on doc03 for auth flow detail, doc17 for storage, doc02/doc10 (GNOME PoC, via the "Mutter failure" row in §99), doc06 (systemd hardening directives), doc11 (testing-strategy overlap for the acceptance-test matrix).

**11. Ambiguities, gaps, internal contradictions**
(a) §19 Revoke All (line 598): "A security epoch increment **is recommended**" — softer language than doc03's unconditional §96 bullet for the same operation. (b) §21 Control-Lease Theft (lines 636–651) states the lease "must include session ID, client ID, security epoch, expiration, capabilities" — omitting `host_id` and `user/user_id`, both present in doc03's `ControlLease` (line 646–667) and in doc00's summarized lease tuple; this is a genuine 3-way field-set disagreement (detailed in Cross-document notes). (c) No T-xxx/formal threat-ID or P0/P1 severity scheme exists despite being the dedicated "threat model" document — only Attacker Classes A–J, Gates A–J, and Assets 4.1–4.10 provide any letter/number identifier structure. (d) The "approximately 2-second hold" (line 830) is the sole concrete numeric UI-timing value in the whole three-document set, yet is immediately hedged as configurable — inconsistent rigor relative to how precisely other invariants are stated. **3. Hard requirements, gates and stop conditions**
§2 Storage Principles (29–52), a 17-item MUST list: minimize persistent data; separate secrets from ordinary config; separate durable identity from ephemeral sessions; never persist active control authority unnecessarily; never persist remote input; never persist passwords; never persist raw TOTP codes; never persist session credentials longer than required; never persist raw control leases unless absolutely required; protect host private keys/TOTP secrets/Access-Key material/trusted-device credentials; make revocation state durable; make security-critical state recoverable after restart; treat corrupted security state as fail-safe; "Do not let the gateway become the source of truth for host security state." §36 never-persist list (above). §40 Secret Store Failure: TOTP unreadable ⇒ "remote authentication unavailable"; Access-Key verifier unreadable ⇒ "new-device authentication unavailable" — explicitly "Do not fall back to weaker authentication." §43 epoch-update ordering: invalidate authority → increment epoch → persist new epoch (or an equivalently safe ordering), "formally reasoned about and tested." §46/58/59: database corruption, unresolved reality-vs-state mismatch, or unproven migration-secret-protection ⇒ **"REMOTE ACCESS = DISABLED"** in all three cases — a repeated, load-bearing fail-safe default. §64: `require_totp = false` "must not be accepted" even via configuration; `disable_emergency = true` "must not silently disable a safety-critical mechanism." §65 Feature Flags: security-critical behavior "must not become an accidental feature flag" (contrasts safe `enable_clipboard=false` vs unsafe `skip_input_isolation=true`).

**4. Technology and library choices**
SQLite suggested, not mandated (§44, 961–984), chosen on "atomicity, concurrency, simplicity, corruption recovery, security, backup behavior, dependency footprint" — "Do not introduce a database merely because the project has several records." `journald` suggested for audit-integrity (§56). "OS secret store" mentioned generically with no concrete keyring/API named. No encryption library, KDF, or signature scheme named anywhere — identical abstraction pattern to doc03/doc09.

**5. Authentication & authorization flow detail (storage-side complement to doc 03)**
Doc17 is not a flow document, but supplies the persistence-side counterpart: TOTP record carries a `configuration_version` for re-enrollment tracking (data011); Access-Key generation mirrors doc03's ≥256-bit/Base64url rule (§16); Access-Key rotation updates `generation, created_at, rotated_at, verifier, status` and explicitly **leaves open** whether rotation also terminates sessions/revokes devices/increments epoch — "Define explicitly whether rotation also: ...increments security epoch. The default should favor security while avoiding unnecessary disruption" (§17, lines 391–399) — a direct textual admission of an undecided design point pushed to implementation time. Recovery-code verification model is hash-based, single-use (§18). The Data Access Matrix (§73) is the definitive "what the gateway sees vs. never sees" table: gateway = No access to host private key/Linux password/TOTP secret/Access-Key verifier/recovery verifier/trusted devices/browser credentials, and only "Limited" access to security epoch/active sessions/control lease.

**6. Threat model detail (storage-fault framing, not adversarial)**
Doc17's "abuse cases" are fault-tolerance oriented rather than adversary-oriented (mapping mostly to doc09's class J "Faulty software"): §36 never-persist list prevents secret leakage via disk; §40 secret-store-failure fails closed rather than degrading auth; §46 Database Corruption (simulate truncated DB, invalid schema, missing table, partial write, FS read failure, disk full) ⇒ REMOTE ACCESS DISABLED + diagnostic, "Do not attempt dangerous automatic reconstruction of security state"; §48 Restore Policy: restoring a backup onto another machine must not silently clone host identity/trust — "require explicit identity decision"; §49 Host Cloning: VM/disk clones must not let two machines share one cryptographic host identity unintentionally — requires "explicit host identity regeneration process"; §63 Secret Rotation During Migration: if migration "cannot prove that a secret is correctly protected" ⇒ REMOTE ACCESS DISABLED.

**7. Data model detail**
*Ownership* (§6, 120–154): `remote-hostd` owns security authority, host identity, authentication state, trusted devices, revocation state, session authority; `gnome-session-agent` owns current GNOME/session state, display topology snapshot, input state, runtime capability state; `remote-gateway` owns only minimal routing/session metadata, "no authentication secrets"; `remote-emergencyd` owns minimal emergency configuration only, "no user authentication database, no browser credentials." *Categories per record*: durable = host identity/private key, configuration, TOTP secret, Access Key verifier, recovery-code state, trusted-device records, security epoch, credential generation/revocation metadata, schema versions (§4, data003); ephemeral = active session, session credential, control lease, WebRTC connection, input/media stream, transition state, temporary auth/display/input state, connection health (§5, data004); never = passwords, raw TOTP/recovery codes, raw input, screen/clipboard content, WebRTC media, browser cookies. *Write strategy*: §41 Atomic Security Updates (900–922) — rotations/updates must use "transactions or atomic replacement," explicitly forbidding the split-state anti-pattern "generation says NEW / verifier says OLD." §42 Crash Consistency (923–938) mandates testing crashes during: Access-Key rotation, trusted-device revocation, revoke-all, security-epoch increment, TOTP configuration, configuration migration, recovery-state update — "After restart, the system must resolve to a safe state." *Migration/versioning*: §11 schema versioning with validation/migration/rollback/unknown-field-handling/defaults; §62 Data Migration must be "versioned, atomic, tested, reversible where practical," validating old schema before and new schema after. *Backup/restore*: §47–48 (1027–1067) — backups may contain host identity/TOTP secret/auth state/trusted devices; no automatic cloud upload; restore must not silently clone identity/trust. *What emergencyd needs* (§69, 1504–1525): only enough local state to revoke authority, increment epoch, lock, restore display, restore input, verify safe state — explicitly must NOT need browser storage, gateway database, WebRTC state, or the remote session database. *Epoch persistence* (§23–24, 518–558): must survive restart, never roll back; if epoch storage is corrupted/unreadable/inconsistent/rolled-back, prefer "REMOTE ACCESS DISABLED" over guessing. *Display snapshot storage* (§30–31, 665–710): `DisplaySnapshot{topology_id, outputs, modes, positions, scale, rotation, enabled_state}` is recovery state, not user configuration, existing only for the duration of a remote session/recovery operation; must be re-validated against current hardware before reapplication (hardware/output/mode/topology-compatibility checks) — "Never force an invalid display configuration."

**8. Tests / verification procedures specified**
§61 Data Model Testing (1341–1362), 13 scenarios: empty DB, valid DB, old schema, future schema, corrupted DB, missing/extra fields, invalid enum, invalid timestamp, duplicate device ID, duplicate host identity, invalid epoch, invalid credential generation. §74 Data Security Tests (1623–1640), 7 assertions: gateway cannot read secrets; GNOME agent cannot read auth DB; emergency daemon cannot read user credentials; ordinary user cannot read protected service secrets; diagnostic bundle contains no secrets; logs contain no secrets; browser cannot obtain secrets — "Also test filesystem permissions independently from application-level authorization." §42 Crash Consistency (7 operations, above). §46 Database Corruption (5 fault scenarios, above). No T-xxx IDs — only section numbers and `data0xx`/`secret001`/`done003`/`agent03`/`final0x` anchors, which (like doc09's anchors) are markdown-generated slugs, not a semantic identifier scheme.

**9. Phase / sequencing guidance and definition-of-done**
§75 Copilot Agent Instructions (1641–1699), 20 numbered rules culminating in an explicit **Implementation order** (agent03 anchor): `DATA MODEL → SCHEMA → CONFIGURATION → SECRET STORAGE → HOST IDENTITY → TRUSTED DEVICES → RECOVERY DATA → SECURITY EPOCH → RUNTIME SESSION MODEL → PERSISTENCE TRANSACTIONS → MIGRATION → CRASH RECOVERY → CORRUPTION TESTING → SECURITY TESTING`. §76 Definition of Done (1700–1737), 28-item checklist spanning durable/runtime/never-persist definitions through secret-leakage tests. §77 Final Data Principle (1738–1793) closes with the load-bearing invariant: "The database or filesystem is not the authority to control the workstation. It is only durable evidence and configuration used by the actual security authority," and the final line of the entire document (line 1794, read separately): **"Nothing stored on disk should be sufficient by itself to regain remote control of the workstation."**

**11. Ambiguities, gaps, internal contradictions**
(a) **Lease schema mismatch** (the most consequential cross-doc issue): doc17's `Lease` (line 624–648: `session_id, client_id, epoch, issued_at, expires_at`) omits both `capabilities` and any `user`/`user_id` field, unlike doc03's `ControlLease` (line 646–667, includes both) and doc00's summarized 8-field tuple. (b) **Struct naming**: `Lease` (doc17, line 631) vs `ControlLease` (doc03, line 653) — same concept, two names, no unification directive anywhere. (c) **Epoch-increment hedging is internally tiered even within this single document**: §21 single-device revocation says "increment security epoch **where appropriate**" (line 494, hedged) while §22 Revoke All states "increment security epoch" as a plain, unconditional step (~line 510–517) — the document treats the *scope* of revocation as determining whether the epoch rule is mandatory or discretionary, but never states this tiering as an explicit rule. (d) §17 Access-Key Rotation (lines 391–399) explicitly defers the epoch-increment-on-rotation question to implementation time — quoted directly above — meaning this is not merely an omission but a documented open design decision. (e) **No hash/KDF algorithm named** anywhere in the dedicated secrets-storage document — the single most consequential specification gap for an implementer, given the user's expectation of "argon2/scrypt/PBKDF2" specifics. (f) **User-field inconsistency across records**: `RemoteSession` (data027) includes a `user` field (line ~565), but `TrustedDevice` (data020) has no explicit user field (only `device_id, host_id`), and `Lease` (data030) also omits `user`/`user_id` — while doc03's `ControlLease` includes `user_id`. This three-way disagreement about whether "user" belongs on the lease/session/device record is unresolved and should be normalized before schema implementation.

**12. Risks and feasibility concerns the doc itself raises**

**5 most decision-relevant insights for implementing `remote-hostd` and secrets storage**

1. `remote-hostd` must be architecturally the *only* holder of TOTP secret / Access-Key verifier / trusted-device credentials / host private key (doc03 §54-55, doc09 §8, doc17 §6 + Data Access Matrix §73) — build the gateway/GNOME-agent IPC boundary first as a narrow, named-operation-only surface (doc03 §74's message list is the concrete contract), never a generic RPC/D-Bus proxy.
2. **Canonicalize one lease/session schema before writing code**, resolving the 3-way field conflict above. Recommended: adopt doc03's 8-field `ControlLease` (`session_id, host_id, user_id, client_id, security_epoch, issued_at, expires_at, capabilities`) as canonical, and treat doc09's and doc17's shorter lists as incomplete restatements rather than alternative designs — otherwise the authorization check in doc03 §75 (`session valid AND client valid AND epoch valid AND lease valid AND CONTROL capability AND state==REMOTE_ACTIVE`) cannot be fully implemented against doc17's persistence-layer struct.
3. Given the cross-document hedging on non-emergency epoch triggers, the security-favoring resolution consistent with the docs' own stated preference ("the default should favor security," doc17 L399) is to **increment the epoch on every credential-invalidating event** — TOTP reset, single trusted-device revocation, Access-Key rotation, password change — not just emergency/disable/revoke-all. Document this as an explicit project decision since no source document commits to it.
4. **No crypto library or algorithm is mandated anywhere** — this is a genuine, undeferred implementation decision (per doc03 §124 "document implementation decisions" and doc17 §75 item 2: "Use secure random generation... use atomic updates"). Before coding, pick and record: a KDF for recovery-code/Access-Key verifier hashing, a signature scheme for host/client identity keypairs, and a TOTP crate — store the decision in repo memory / `docs/security/architecture.md` since the specs explicitly decline to choose.
5. **Secret-store failure and data corruption must both fail to "REMOTE ACCESS DISABLED"** (doc17 §24/§40/§46/§59), never a degraded-but-functional mode. Implementing this as a wrapping invariant around the `SecretStore` abstraction (`get_secret/set_secret/delete_secret/rotate_secret`, doc03 §54/doc17 §38) automatically satisfies a large share of doc09's Gates A/B/E and doc03's acceptance tests §113-121 without any GNOME/network integration.

**Which security items can be built and unit-tested with no GNOME/network dependency (pure logic), recommended order**

1. Data structures + schema validation/versioning (`HostIdentity, SecurityConfig, TOTP record, RemoteAccessKey, TrustedDevice, RemoteSession, Lease/ControlLease, RecoveryMarker, DisplaySnapshot`) and `schema_version` migration logic (doc17 §11, §60-63) — pure serialization, zero I/O beyond disk.
2. `SecretStore` abstraction with atomic-write semantics (rename+fsync or transaction) and crash-consistency fault injection (doc17 §41-42, §38-40) — testable with temp dirs and simulated truncation/kill, no PAM/GNOME/network.
3. Security-epoch persistence + anti-rollback + the epoch-comparison authorization check (`session.epoch == current_security_epoch`, doc03 §33) — pure integer/state-machine logic.
4. Remote Access Key generation (CSPRNG ≥256-bit, Base64url), verifier hashing, and verification (doc03 §15-18, doc17 §15-17) — pure logic once a KDF is chosen.
5. TOTP secret generation, provisioning-URI/QR construction, and RFC-6238 verification including clock-skew-window and same-timestep-replay rejection (doc03 §9-13, doc09 L522) — fully testable with synthetic clocks, no GNOME/network.
6. Recovery-code generation, hashing, single-use invalidation (doc03 §57-59, doc17 §18) — pure logic.
7. Trusted-device CRUD + revocation state transitions (doc17 §19-22) — pure logic against the storage layer from step 2.
8. Control-lease issuance/renewal/expiration/epoch-validity and the full authorization boolean formula (doc03 §75) — pure state-machine logic; this also unit-tests doc09's Reconnect Race (§25), Security-Epoch Attack (§23), and Emergency Race (§24) as pure concurrency/clock tests.
9. PAM authentication itself (doc03 §6-8) is the first item requiring a real external dependency (libpam/system account) — but the rate-limiting/lockout/generic-error wrapper logic around it (doc03 §39-41) can still be unit-tested by mocking the PAM boundary.
10. IPC message (de)serialization and malformed-input rejection (doc03 §74, doc09 abuse case §88) — pure parsing/fuzz-testable logic, no live transport needed.

This ordering builds the entire `remote-hostd` security core and secrets-storage layer bottom-up with zero GNOME/Wayland/network dependency, deferring only the PAM syscall boundary and later D-Bus/session-agent integration to a follow-on phase — consistent with the `governed` validation tier and "smallest affected check" guidance already active for this repo per [AGENTS.md](AGENTS.md).
