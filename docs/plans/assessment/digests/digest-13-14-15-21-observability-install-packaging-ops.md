### 13 — OBSERVABILITY, DIAGNOSTICS & TROUBLESHOOTING

**1. Purpose & scope.** Defines how the system makes every remote-session incident answerable — state, transition, cause, responsible/failed component, whether remote authority was revoked, whether the session/display/input were restored, and why recovery succeeded or failed — while never exposing passwords, TOTP secrets, Remote Access Keys, trusted-device credentials, session tokens, control leases, or private browser credentials. Scope covers structured logging, severity levels, error-code taxonomy, capability/health reporting, a diagnostic CLI, diagnostic bundles, troubleshooting decision trees, and observability-of-observability tests.

**2. Named identifiers defined.**
- *Components with health state*: `remote-hostd`, `remote-gateway`, `gnome-session-agent`, `remote-emergencyd`, PipeWire, Mutter/GNOME Shell, networking subsystem, WebRTC session, authentication subsystem (§4).
- *State-transition event fields* (§6, id=`w9q4b3`): `timestamp`, `event`, `previous_state`, `new_state`, `transition_id`, `trigger`, `component`, `result`, `failure_code`.
- *Structured log fields* (§7, id=`w3dr7e`): `timestamp`, `severity`, `component`, `event`, `state`, `transition_id`, `session_id`, `client_id`, `security_epoch`, `result`, `error_code`, `duration_ms`; optional `gnome_version`, `mutter_version`, `pipewire_version`, `kernel_version`, `gpu_identifier`, `display_count`, `virtual_display_state`, `network_state`.
- *Severity levels* (§8): `DEBUG`, `INFO`, `NOTICE / WARNING` (grouped as one tier), `ERROR`, `CRITICAL`.
- *Correlation identifiers*: `session_id = rs_01J...` (§11, id=`g3y0s5`); `transition_id = tr_01J...` (§12, id=`q0v9x7`).
- *Capability report states* (§16, id=`r7h2kp`): `SUPPORTED`, `AVAILABLE`, `UNKNOWN`, `FAILED`, `NOT AVAILABLE`; overall `SUPPORTED`.
- *Diagnostic CLI candidate subcommands* (§23, line 789): `status health capabilities session display input network security logs self-test version` — explicitly "should follow repository conventions," i.e., not final.
- *Error codes* (§34): `AUTH_INVALID_PASSWORD`, `AUTH_INVALID_TOTP`, `AUTH_ACCESS_KEY_REQUIRED`, `AUTH_ACCESS_KEY_INVALID`, `AUTH_DEVICE_REVOKED`, `SESSION_NOT_FOUND`, `SESSION_EPOCH_MISMATCH`, `LEASE_EXPIRED`, `LEASE_REVOKED`, `GNOME_SESSION_UNAVAILABLE`, `MUTTER_INTERFACE_UNAVAILABLE`, `VIRTUAL_MONITOR_FAILED`, `DISPLAY_ISOLATION_FAILED`, `INPUT_ISOLATION_FAILED`, `SESSION_LOCK_FAILED`, `PIPEWIRE_UNAVAILABLE`, `WEBRTC_FAILED`, `NETWORK_UNAVAILABLE`, `EMERGENCY_TRIGGERED`, `EMERGENCY_RECOVERY_FAILED`, `DISPLAY_RESTORE_FAILED`, `INPUT_RESTORE_FAILED`.
- *Failure classification taxonomy* (§37): `AUTHENTICATION, AUTHORIZATION, SESSION, GNOME, MUTTER, PIPEWIRE, INPUT, DISPLAY, NETWORK, WEBRTC, SYSTEMD, PRIVILEGE, CONFIGURATION, HARDWARE, RECOVERY, SECURITY, UNKNOWN`.
- *Diagnostic Test Levels* (§48): Level 1 Status, Level 2 Self-Test, Level 3 Integration Test, Level 4 Remote Session Test, Level 5 Hardware Safety Test.
- *Diagnostic API operations* (§52): `get_status()`, `get_capabilities()`, `get_health()`, `get_recent_events()`.
- *DiagnosticEvent data model* (§53, id=`4x3v2z`): `timestamp, event_type, severity, component, state, transition_id, session_id, security_epoch, result, error_code, metadata`.
- Anchor-style `id="..."` attributes appear on ~20 code blocks (e.g., `u2bqgm`, `a8p6d2`, `g5x1rz`, `z4p2xc`) — these are markdown anchors, not a formal procedure/test-ID scheme.
- No package names, file paths, systemd unit names, users/groups, or config keys appear anywhere in this document — it is entirely behavioral/schema-level.

**3. Hard requirements, gates and stop conditions.**
- MUST NOT log: passwords, TOTP secrets, Remote Access Keys, trusted-device secrets, session tokens, control leases, raw authentication headers, actual keyboard content, screen captures, clipboard contents (§6, §9, §19, §28).
- MUST NOT infer support merely because a D-Bus interface exists (§16); MUST prefer capability detection over version branching (§17).
- Diagnostic bundle MUST NOT contain passwords/TOTP secret/Remote Access Key/recovery codes/trusted-device secrets/session tokens/control leases/browser cookies/private keys/clipboard/screen captures/keyboard contents (§28).
- MUST NOT collect by default: app names (unless necessary), window titles, document names, unrelated file paths, clipboard, screen contents, keystrokes, mic/audio (§31). MUST NOT introduce cloud telemetry merely for debugging convenience (§31).
- MUST NOT expose detailed host diagnostics to an unauthenticated browser (§32); MUST NOT expose internal stack traces to users (§33).
- Debug/diagnostics MUST NOT extend leases, disable auth, disable rate limits, bypass authorization, prevent emergency recovery, keep sessions alive, or disable display/input restoration (§51).
- Diagnostic API MUST authenticate local callers, be read-only by default, and reject arbitrary command parameters — explicitly reject a `diagnostic.execute(command)` pattern (§52).
- MUST NOT hide Level 5 (hardware-affecting) tests behind a generic `health` command (§48); destructive tests require explicit test mode, never silent execution via normal health check (§26).
- MUST NOT report success/"cleanup completed" when only some recovery steps completed (§21–22).

**4. Technology and library choices.** Notably tech-agnostic. Logging: "Use systemd/journald **or** the project's established logging infrastructure" (§30) — journald is suggested, not mandated exclusively; "JSON" is never mentioned (0 hits); only "structured logging"/"structured events"/"structured journald logs" (§53, §7). No tracing framework named. No CLI framework named. No signing/CI mentioned (out of scope for this doc). Exact CLI command names are explicitly deferred: "The exact command names should follow repository conventions" (§23).

**5. Detail — event taxonomy, redaction, correlation, bundle, decision trees, health checks.** Event taxonomy spans security events (authentication success/failure, TOTP/Access-Key failure, trusted-device registration/revocation, session/lease creation/expiry/revocation, epoch increment, emergency activation, stale-credential rejection, replay rejection, rate-limit activation, unauthorized IPC, privilege-boundary violation — §9) and an incident-timeline example (§38, id=`5r4x2n`) chaining `AUTHENTICATED → SESSION_CREATED → LEASE_CREATED → VIRTUAL_DISPLAY_CREATED → PHYSICAL_DISPLAY_DISABLED → PHYSICAL_INPUT_DISABLED → WEBRTC_CONNECTED → REMOTE_ACTIVE` then `NETWORK_LOSS → LEASE_EXPIRED → REMOTE_AUTHORITY_REVOKED → SESSION_LOCKED → DISPLAY_RESTORED → INPUT_RESTORED → LOCAL_LOCKED`. Redaction (§29) is explicitly secondary defense — hash/truncate identifiers (e.g., `client_id: 8f21...b92a`) rather than rely on post-hoc filtering; primary defense is deliberate exclusion (§1, §11). Correlation uses `session_id`/`transition_id` (§11–12) plus security-epoch cross-checks (§13, id=`m0j3qa`: compare `Security Epoch` vs `Session Epoch` vs `Lease Epoch` to explain `REVOKED` results) and control-lease metadata display that never includes the credential itself (§14). The diagnostic bundle (§28, id=`q4v7mk`) = system info, service status, capability report, recent structured logs, state history, recent failure codes, GNOME/Mutter/PipeWire diagnostics, network diagnostics, config schema/version. Troubleshooting decision tree (§35, id=`5j7x3m`) walks reachability→auth→session authorization→GNOME prep→display isolation→input isolation→PipeWire/WebRTC→`REMOTE_ACTIVE`. Six named failure scenarios A–F (§36): (A) auth OK/remote doesn't start; (B) video OK/input doesn't (never fix by "blindly granting broader privileges"); (C) physical keyboard still controls GNOME — explicitly "**critical safety issue**," classify **P0**, block release; (D) physical display remains visible — privacy/safety failure, must not be "solved" by a fullscreen black window without changing the security model; (E) disconnect leaves workstation unlocked — safety failure; (F) emergency shortcut fails — critical operational failure, must not depend on browser/network. Health checks are non-destructive by definition (§25–26); Level 5 hardware-safety tests require explicit operator intent (§48).

**6. Tests/verification.** §54 Test Requirements for Observability (10 unlabeled checks). §55 Observability Acceptance Tests, id=`g5x1rz` (18-item checklist, e.g. state observable, security events logged, secrets never appear, diagnostic commands don't alter state). §57 Definition of Done, id=`z4p2xc` (18 items). No formal `TC-###`-style test IDs — only section numbers and anchor ids.

**7. Phase/sequencing guidance and DoD.** §56 gives a 9-stage pipeline: `RESEARCH → DESIGN OBSERVABILITY → IMPLEMENT STRUCTURED EVENTS → ADD SECURITY REDACTION TESTS → ADD CLI/STATUS OUTPUT → INTEGRATE WITH SYSTEMD/JOURNAL → TEST FAILURE PATHS → VERIFY NO SECRET LEAKAGE → DOCUMENT ERROR CODES`. DoD (§57) requires state/transition/session/epoch/lease/GNOME-capability/display/input/emergency all observable, failures classified, secrets excluded, diagnostic API authorized, CLI safe, bundle safe, crash/restart diagnosable, fault-injection tests present, hardware failures investigable.

**8. Cross-references.** Implicit only: shares components/states with doc 00; §56 says "Follow the existing logging, CLI, service, and test conventions" (i.e., defers to whatever doc 15/repo established); scenario classification (P0 for physical-keyboard bypass) implies doc 09 (threat model) and doc 18 (red-team plan) severity alignment, though never named directly.

**9. Ambiguities, gaps, contradictions.** No canonical CLI binary name is ever fixed — and critically, doc 13's own diagnostic-CLI vocabulary at line 789 (`status health capabilities session display input network security logs self-test version`) **differs** from doc 21's canonical operational vocabulary at line 902 (`status doctor sessions revoke-session revoke-all disable enable emergency-status compatibility diagnostics`): "health" vs "doctor," "capabilities" vs "compatibility," and doc 13's list has no session-control verbs (`revoke-session`, `revoke-all`, `disable`, `enable`) while doc 21's has no read-only introspection verbs (`session`, `display`, `input`, `network`, `security`, `logs`, `version`). Only `status` and (conceptually) `diagnostics`/`logs` overlap. This could reflect two separate tools (diagnostic vs control) or one merged CLI — the docs never say. Retention values are never quantified: "Define: maximum log volume, retention period... The exact values should be configurable and documented" (§30) — no numbers given. Severity tier "NOTICE / WARNING" is combined as one bullet, ambiguous whether these map to one or two syslog/journald priority levels.

**10. Risks/feasibility concerns raised by the doc itself.** Diagnostic tooling risks becoming "an administrative command-execution interface" if not deliberately scoped away from that (§2 item 10, §52). GNOME/Mutter's private/unstable APIs make version-based branching fragile — capability detection is required instead (§17), echoing doc 00's Wayland feasibility concerns. DEBUG logging could increase "metadata collection" in ways that raise privacy concerns, requiring explicit warnings (§50). The emergency path's independence from gateway/network is repeatedly flagged as something that must be true, not merely aspired to (§2 item 7, §36 Scenario F).

### 14 — INSTALLATION, SETUP, CONFIGURATION & FIRST-RUN EXPERIENCE

**1. Purpose & scope.** Governs install → first-run wizard → security setup → explicit enablement → uninstall, enforcing the invariant: "**A workstation must never become remotely controllable merely because the software was installed.**" Covers preflight detection, privilege separation, TOTP/Remote-Access-Key/recovery-code/trusted-device setup, emergency-controller verification, network/TLS setup, safe defaults, upgrade/uninstall/reset behavior, and a full first-run acceptance test.

**2. Named identifiers defined.**
- *Supported environment* (§2): Ubuntu 26.04 LTS, Ubuntu Desktop, GNOME 50+, Wayland, systemd, single-user workstation.
- *Components provisioned* (§5): `remote-hostd`, `remote-gateway`, `remote-emergencyd`, `gnome-session-agent` (no `.service` suffixes here, unlike doc 15).
- *Runtime privilege model* (§6): `remote-gateway` = UNPRIVILEGED; `remote-hostd` = NARROW SYSTEM PRIVILEGE; `gnome-session-agent` = NORMAL USER SESSION; `remote-emergencyd` = MINIMAL PRIVILEGED SERVICE.
- *Host identity display example* (§13): `Host ID: rc_8f21...`, `Fingerprint: AB73-19D4-...` (fingerprint for recognition only, never treated as the auth secret).
- *Default emergency shortcut* (§24): `Ctrl + Alt + Shift + F12`, hold duration `2 seconds` (both explicitly configurable).
- *Remote Access Key*: ≥ `256 bits` of entropy (§19), generated automatically, never user-invented.
- *Setup Failure States* (§50): `NOT_CONFIGURED, CONFIGURATION_REQUIRED, UNSUPPORTED, PARTIALLY_CONFIGURED, SAFETY_CHECK_FAILED, READY, REMOTE_ACCESS_DISABLED`.
- *Installer exit codes* (§55): `SUCCESS, UNSUPPORTED_PLATFORM, MISSING_DEPENDENCY, PERMISSION_ERROR, CONFIGURATION_ERROR, SECURITY_SETUP_REQUIRED, SAFETY_CHECK_FAILED, INSTALLATION_FAILED` (numeric values deferred to "repository conventions").
- *Setup Security Gates A–L* (§57): A Supported platform; B Valid GNOME session; C Authentication configured; D TOTP verified; E Remote Access Key configured; F Emergency controller verified; G Virtual display capability verified; H Physical display isolation verified; I Remote input verified; J Physical input isolation verified; K Recovery verified; L Configuration valid.
- *Configuration Model categories* (§38): Security / Remote Session / Network / Safety / Diagnostics (no file, no keys named).
- *Recovery-path conceptual verbs* (§46, line 1265): `diagnose repair disable reset uninstall`.
- Reset tiers (§47): Soft Reset, Security Reset, Full Reset.
- No package name, config file path, systemd unit filenames, or Unix user/group strings appear anywhere in this document — **and, confirmed by grep, this is the only one of the four documents with zero `id="..."` anchor attributes on any code block**, unlike 13/15/21.

**3. Hard requirements, gates and stop conditions.**
- MUST start with Remote Access = DISABLED post-install, until every Setup Security Gate A–L passes (§3, §57).
- MUST NOT auto-repair the workstation: no automatic firewall changes, GPU driver replacement, unrelated GNOME setting changes, disabling security software, display reconfiguration, or unrelated systemd service changes (§8).
- TOTP MUST remain mandatory even for trusted devices — trusted status "must never bypass TOTP" (§14, §22).
- TOTP secret MUST NOT be sent over the remote network during normal operation (§15); MUST NOT be exposed to the browser (§17).
- Emergency controller verification is a **hard safety dependency**: "If the emergency controller cannot be verified: Remote Access: MUST REMAIN DISABLED... The setup wizard must not declare the workstation ready" (§27).
- MUST NOT silently downgrade TLS to plain HTTP (§31); any auto-created firewall rule MUST be minimal/documented/reversible, and the firewall must never be silently disabled (§32).
- MUST NOT store secrets in environment variables (§52) or command-line arguments, e.g. explicitly rejects a `remote-tool --access-key SECRET` pattern (§53).
- Failed configuration migration MUST result in Remote Access = DISABLED and MUST NOT silently discard security configuration (§43).
- Uninstall MUST terminate sessions/revoke authority/lock GNOME/restore display & input/stop services **before** removing files (§44); MUST NOT leave remote control active indefinitely if uninstall fails halfway (§45).
- Reboot MUST NOT auto-resume remote control; all sessions/leases/browser trust become invalid (§41). First remote connection MUST NOT auto-trust the first browser (§35).

**4. Technology and library choices.** Explicitly permissive/deferred: "A simple native Linux UI or CLI is acceptable for initial releases. Do not make a heavyweight desktop application a prerequisite for the core host" (§11). No installer language (shell/Rust/Python) is named anywhere. No secret-storage library named (only "appropriate local secret-storage mechanism," §17). No TLS library, no QR-code library named. This document is purely behavioral/UX, deferring all implementation-technology choices to "the project architecture"/"repository conventions."

**5. Detail — install/first-run sequence, TOTP UX, Remote Access Key, recovery codes, emergency config, capability verification, "explicit enable," uninstall.** Lifecycle (§3): `INSTALL → ENVIRONMENT CHECK → SERVICE INSTALLATION → CONFIGURATION INITIALIZATION → SECURITY SETUP → GNOME SESSION VALIDATION → EMERGENCY CONTROLLER VALIDATION → NETWORK/TLS SETUP → SELF-TEST → EXPLICIT ENABLE REMOTE ACCESS → READY`. First-run wizard (§11) has 11 explicit steps ending in explicit enablement. TOTP UX (§15–17): generate secret → QR code (+ manual key) → verify current code → confirm; on failure, retry loop, never enable access (§16); protect via restrictive file permissions + service-identity separation + no logs + no browser exposure (§17). Remote Access Key (§19–21): auto-generated, ≥256-bit, shown only on explicit request, excluded from logs; backup guidance explicitly says save it in a password manager and avoid screenshots/plaintext notes/localStorage/URLs/source code (§20); rotation invalidates the old key while, per the *preferred model*, existing trusted devices remain trusted unless explicitly revoked and active sessions continue until lease expiry unless policy demands immediate revocation — plus an explicit "rotate and revoke all" operation (§21). Recovery codes (§18): cryptographically random, single-use, shown only at setup, explicitly acknowledged, invalidated after use; must not silently become a permanent TOTP replacement. Emergency controller config (§24–27): verifies `remote-emergencyd` installed+running, input monitoring available, shortcut configured (default `Ctrl+Alt+Shift+F12`, 2s hold), and requires an explicit destructive test that locks the workstation — with the explicit safety escape hatch that failure to verify blocks "READY" entirely. Capability verification is the preflight table (§7): Platform/Desktop/GNOME Version/Session/systemd/User Session/Mutter/PipeWire/libei-EIS/Graphics → PASS/FAIL → Overall INSTALLABLE/UNSUPPORTED. "Explicit enable" semantics (§33, §57): all gates pass → explicit user confirmation required → enable. Uninstall (§44–45): distinguishes "remove software" vs "remove configuration and credentials," fails safe if interrupted.

**6. Tests/verification procedures.** §56 First-Run Acceptance Test — 26 explicit numbered steps from install through emergency takeover, stale-session-rejection check, and final verification that "original GNOME session remains intact." No formal test-ID scheme; gates A–L (§57) are the closest thing to named verification checkpoints.

**7. Phase/sequencing guidance and DoD.** §58 implementation sequence: `RESEARCH → PREFLIGHT DETECTION → PACKAGE/SERVICE INSTALLATION → CONFIGURATION MODEL → SECURITY INITIALIZATION → EMERGENCY CONTROLLER → GNOME CAPABILITY VALIDATION → NETWORK/TLS SETUP → SELF-TEST → EXPLICIT ENABLE → FIRST REMOTE CONNECTION → UPGRADE/UNINSTALL TESTING`. DoD (§59) is a 28-item checklist. Final principle (§60): `INSTALL → CONFIGURE → VERIFY → EXPLICITLY ENABLE → REMOTE ACCESS`, never `INSTALL → REMOTE ACCESS AVAILABLE`.

**8. Cross-references.** References `adaptive-workflow-configurator` twice (§6/L132, §58/L1629). Shares components/gate vocabulary with doc 13 (self-test/capability report) and doc 15 (upgrade/uninstall/service-installation parity) and doc 21 (the "disable remote access" recovery command, §46/§48, is functionally identical to doc 21's `disable` verb).

**9. Ambiguities, gaps, contradictions.** File ends mid-sentence at line 1747: "The most important first-run invariant is:" — no closing statement follows (file truly ends at line 1748, confirmed by grep). §46's recovery-verb list (`diagnose repair disable reset uninstall`, line 1265) is a **third, non-overlapping CLI vocabulary** vs. doc 13's (line 789) and doc 21's (line 902) — it introduces `repair` and `reset`, absent from both other lists, and omits `doctor/health`, `sessions`, `revoke-session`, `revoke-all`, `enable`, `compatibility`, `emergency-status`. This document is also the only one of the four with **no `id="..."` anchors at all**, a formatting inconsistency versus 13/15/21.

**10. Risks/feasibility concerns.** Emergency-controller verification as a hard blocking gate (§27) means first-run setup can never complete on hardware/GNOME combinations where the emergency mechanism can't be verified — a real feasibility risk for edge-case hardware not yet flagged elsewhere. NAT traversal/rendezvous/STUN/TURN are deferred to "eventually" (§28-30), meaning true non-LAN internet access is explicitly out of initial scope. The 26-step first-run acceptance test (§56) implies a substantial hardware/VM test-automation investment not yet designed.

### 15 — PACKAGING, DISTRIBUTION, UPDATES & RELEASE ENGINEERING

**1. Purpose & scope.** Packaging is explicitly framed as "part of the security architecture" since the package installs system services, privileged components, a GNOME session agent, an emergency daemon, auth configuration, and browser-facing services. Governs distribution target, dependency declaration, upgrade/downgrade/rollback safety, protocol/version compatibility, signing, SBOM/provenance, release channels, GNOME/GPU compatibility matrices, and the release-candidate checklist.

**2. Named identifiers defined.**
- *Distribution target* (§2): Ubuntu 26.04 LTS, Ubuntu Desktop, GNOME 50+, Wayland, systemd, `x86_64` initially.
- *Primary artifact* (§3): `.deb`. Future: APT repository, Ubuntu PPA, "Signed release repository," containerized dev environment, source distribution — containers explicitly rejected as the *primary host deployment mechanism*.
- ***systemd unit names — the only concrete unit names in the whole four-document set*** (§12, line 299, id=`svc001`): `remote-hostd.service`, `remote-gateway.service`, `remote-emergencyd.service`; plus "appropriate user-session integration for" `gnome-session-agent` (§12, id=`svc002`) — **no `.service` suffix given for `gnome-session-agent`**, leaving its unit form (systemd `--user` unit? GNOME Shell extension? autostart entry?) unspecified.
- *Package installation states* (§10, id=`pkg001`): `NOT_INSTALLED, INSTALLED, PARTIALLY_CONFIGURED, CONFIGURED, READY, DISABLED, FAILED_SAFE`.
- *Config schema version example* (§17, id=`cfg001`): `schema_version = 3` — explicitly illustrative, not an authoritative starting value.
- *Protocol compatibility example* (§22, id=`proto001`): client/host protocol version numbers 1/2/3 with compatible/policy-dependent/reject outcomes.
- *Compatibility matrix* (§34): table columns `Ubuntu | GNOME | Wayland | Status`, e.g. `26.04 | 50.x | Yes | Supported`.
- *Release channels* (§32, id=`channel01`): `stable, beta, nightly/development`; initial project needs only `stable` + `development`; development builds must display `DEVELOPMENT BUILD` (§52, id=`dev001`).
- *Release provenance fields* (§56, id=`prov001`): Git revision, source archive checksum, package checksum, build environment, dependency lock/version state, release date, release channel, signing identity.
- *Test/checklist anchors*: Package Upgrade Security Test id=`upg003` (§42), Package Removal Test id=`uninstall01` (§43), Release Candidate Checklist id=`rc001` (§45), Packaging CI id=`ci001` (§53), Clean-Machine Installation Test id=`clean001` (§54), Upgrade-Matrix Test id=`matrix01` (§55), Definition of Done id=`done001` (§58).
- **No package name is ever given** (e.g., no "blackroom-console" string appears — confirmed by grep). **No signing technology is named** — no "GPG," no "sigstore" (confirmed absent); only "cryptographically signed," "signed repository metadata," "trusted signing keys." **No packaging tool is named** — no "dpkg," "debhelper," or "cargo-deb" anywhere despite ".deb" being mandated as the artifact format.

**3. Hard requirements, gates and stop conditions.**
- MUST NOT release if: remote authority survives a critical failure; emergency recovery fails; physical input/display isolation is unreliable; stale sessions reconnect; security epoch is bypassable; packaging weakens privileges; upgrade leaves remote control active unexpectedly; secrets appear in logs/artifacts; package permissions are unsafe; critical GNOME compatibility is unknown; rollback leaves an uncertain state (§46).
- MUST NOT claim compatibility with arbitrary Debian/Ubuntu versions, KDE, wlroots, X11, or other architectures without dedicated validation (§2); "Passing compilation is not sufficient" for GNOME/Mutter compatibility claims (§33).
- MUST NOT auto-expose a remote endpoint before first-run security setup, even immediately post-install (§11).
- Dependency validation MUST fail clearly (e.g. PipeWire MISSING → Remote Access DISABLED) rather than attempt unsafe fallback (§9).
- Upgrade MUST follow: disable new connections → revoke/terminate active sessions → lock GNOME → restore display → restore input → stop old services → install → migrate config → validate → start → health check → **remote access remains disabled** → explicit re-enable (§15). MUST NOT allow upgrade scripts to leave remote control active while replacing critical components.
- Old emergency daemon MUST NOT be removed before the replacement is verified operational, unless already safely disabled (§37).
- Maintainer scripts (pre/post-install) MUST be "extremely small" — no complex application logic in them (§38); MUST NOT dynamically construct shell commands from configuration values (§39).
- Client MUST be rejected, not downgraded, if it can't meet newer security requirements (e.g., old client without TOTP support → REJECT, §23) — explicitly forbids a "legacy client mode" that weakens authentication without a separately designed security model.
- Never instruct users to bypass package signature verification (§26).

**4. Technology and library choices.** ".deb" is the *mandated* primary artifact (§3: "the initial production distribution should preferably use a native Debian/Ubuntu package"). Everything else is deferred: no CI system named (§53 lists required CI *checks*, not a tool), no signing mechanism named (§26–27), no SBOM tool named (§31), reproducible builds are "where practical" (aspirational, not mandatory — §29). "Before implementing packaging, Copilot Agent must inspect the workflow produced by `adaptive-workflow-configurator`" (§4/L105) — i.e., tooling choice is explicitly punted to repo conventions.

**5. Detail — package split, dependencies, versioning, upgrade state machine, rollback, migration, interrupted-upgrade recovery, release checklist, signing.** Package split (§4, id=`pkgx01`): one package containing `remote-hostd`, `remote-gateway`, `remote-emergencyd`, GNOME session agent, systemd units, config schema, diagnostic tooling, docs — "exact package/file layout must follow the repository's established packaging architecture" (no split into multiple .debs specified). Dependencies (§8): systemd, PAM, PipeWire, libei/EIS, GNOME/Mutter components, networking/TLS deps, runtime libraries — categories only, no version pins given. Versioning (§6, id=`vrs001`) explicitly separates project version / package version / protocol version / config-schema version — "Do not assume application version == protocol version." Upgrade state machine (§15, id=`upg001`) given above; interruption testing (§16, id=`upg002`) enumerates package-install interrupted, service-restart interrupted, config-migration interrupted, disk full, permission error, dependency failure, reboot-during-upgrade — "If the system cannot prove that remote access is safe: REMOTE ACCESS = DISABLED." Migration (§17–19): `OLD CONFIG → VALIDATE → MIGRATE → VALIDATE NEW CONFIG → ACTIVATE`; secret migration must never print/copy-to-world-readable/pass-via-CLI/log/expose-to-gateway secrets. Rollback (§20) has four levels — Application, Package, Configuration, Security — and explicitly "must never assume rollback automatically restores remote authority safely." Downgrade (§21, id=`dwg001`) requires full teardown *before* installing the older version, and REMOTE ACCESS = DISABLED if config compatibility is uncertain. ### 21 — OPERATIONAL RUNBOOK, RECOVERY AND INCIDENT RESPONSE

**1. Purpose & scope.** The most CLI/procedure-concrete of the four documents. Defines day-to-day operation, failure handling per component, credential-compromise response, incident severity/response procedure, and the canonical "safe" operational verbs. Core rule: "**When in doubt, disable remote control and return the workstation to a locked local state**" (§2, id=`8a7p2k`).

**2. Named identifiers defined.**
- *Operational states* (§3, id=`2jz1xm`, line 57): `LOCAL_ACTIVE, LOCAL_LOCKED, REMOTE_ACTIVE, REMOTE_DEGRADED, TEARING_DOWN, RECOVERING, EMERGENCY, FAILED_SAFE, DISABLED, INCOMPATIBLE`.
- *Readiness-check command* (§6, id=`q17p0a`, line 150): **`remote-access status`** — the only place across all four docs where a concrete binary-name-plus-subcommand string appears.
- *Session-management commands* (§31): **`remote-access sessions`**, **`remote-access revoke-session <session>`** ("or equivalent implementation-specific interfaces").
- ***Canonical operational CLI verb list*** (§40, id=`x4yq8f`, line 902): **`status, doctor, sessions, revoke-session, revoke-all, disable, enable, emergency-status, compatibility, diagnostics`** — explicitly labeled "Good examples." Explicitly rejected generic verbs (id=`8q7j1r`): `run-command, exec, shell, dbus-proxy`. This list matches the doc-00 operational-actions summary given in the task context essentially verbatim, confirming doc 00/doc 21 agreement.
- *Incident severity levels* (§51): `CRITICAL, HIGH, MEDIUM, LOW`, each with concrete example incidents (CRITICAL includes "stale session successfully reactivated"; HIGH includes "security epoch failure"; MEDIUM includes "diagnostic exposure without credentials"; LOW is "operational inconvenience").
- *Operational Recovery Levels* (§50, line 1204): `LEVEL 0 Normal, LEVEL 1 Degraded, LEVEL 2 Recovery, LEVEL 3 Emergency, LEVEL 4 Failed Safe, LEVEL 5 Security Incident` — a **second, parallel taxonomy** to the Operational States of §3, never explicitly mapped 1:1 (e.g. LEVEL 3 ≈ `EMERGENCY`, LEVEL 4 ≈ `FAILED_SAFE`, but the doc doesn't say so).
- *Incident Response Procedure* (§52, id=`n88prc`): `CONTAIN → REVOKE → LOCK → RESTORE → VERIFY → PRESERVE EVIDENCE → INVESTIGATE → ROTATE CREDENTIALS → PATCH → TEST → REVALIDATE → RE-ENABLE EXPLICITLY`.
- ~17 additional anchor `id="..."` blocks (`3ghx1k`, `8n9t4w`, `q4b0yd`, `l0fsby`, `3by7s1`, `w2l6bc`, `gjx9ma`, `8n1s5u`, `b3e9qs`, `lry9ut`, etc.) — again markdown anchors, not formal RUNBOOK-### procedure IDs.
- No package names, systemd unit names, file paths, or recovery-marker files are given anywhere in this document — all "state" is described logically/conceptually, never tied to an on-disk marker.

**3. Hard requirements, gates and stop conditions.**
- NEVER prioritize restoring remote connectivity over proving the workstation is safe (§1). Preferred failure path is invariant: `PROBLEM → REVOKE → LOCK → RESTORE DISPLAY → RESTORE INPUT → VERIFY → LOCAL_LOCKED` (§2).
- Any critical readiness-check failure MUST yield `NOT_READY`, never "best-effort activation" (§6).
- Host daemon crash MUST NOT let remote authority "automatically become valid again" on restart; `REMOTE_CONTROL = DISABLED` until fresh authentication (§12, id=`8n9t4w`).
- Display/input restoration failure MUST NOT be resolved by re-enabling remote control (§16–17) — retries are bounded, then requires local admin intervention.
- Emergency action MUST NOT unlock the workstation — user must perform normal GNOME authentication afterward (§18, id=`l0fsby`).
- A compromised host "cannot be made trustworthy merely by restarting the remote service" (§26) — full procedure required (isolate, investigate, regenerate host identity/keys/TOTP, revalidate, only then re-enable).
- Revoking a remote trusted device MUST NOT require physical access to the workstation (§23).
- Credential rotation MUST NOT create a window where both old and new credentials have broader authority than intended (§45, id=`w2l6bc`).
- Management interface MUST NOT become "a privileged command-execution framework" (§40) — explicit rejection of generic verbs.
- MUST NOT require the administrator to diagnose root cause before revoking authority during a suspected incident (§48, id=`gjx9ma`); "Never skip containment because the incident appears minor" (§52).
- Recovery/re-enable MUST wait until the full Recovery Verification Checklist (§49, 22 items across Security/GNOME/Display/Input/Services/Compatibility) passes.
- **Copilot Stop Conditions** (§57) — must stop and report (not invent a workaround) if: a recovery action would require arbitrary shell execution; emergency depends on the main remote stack; revocation cannot be guaranteed; stale sessions can survive recovery; display/input restoration cannot be verified; the system cannot establish a known safe state; upgrade can leave remote authority ambiguous; credentials cannot be safely rotated; diagnostics expose secrets; documented procedure doesn't match implementation.

**4. Technology and library choices.** None specified — this document is pure procedure/behavior. No CLI framework, no metrics/monitoring stack (§43 lists metric *names* conceptually, not a tool), no incident-management tooling named.

**5. Detail — every runbook procedure, incident-response flow, recovery per failure class, disable/revoke/rotate, evidence.** Per-failure-class recovery procedures are individually specified: Network failure (§9: detect → stop input per policy → `REMOTE_DEGRADED` → bounded recovery attempt → else revoke/lock/restore/verify → `LOCAL_LOCKED`/`FAILED_SAFE`); Client browser crash (§10); Gateway failure (§11, id=`3ghx1k` — "host must not depend on gateway availability to revoke authority... emergency controller must continue functioning"); Host daemon crash (§12); GNOME agent crash (§13); PipeWire failure (§14, id=`q4b0yd` — "capture unavailable must not mean remote authority remains active indefinitely"); Mutter/GNOME failure (§15); Display restoration failure (§16); Physical input restoration failure (§17). Emergency takeover flow (§18, id=`l0fsby`): `PHYSICAL EMERGENCY SHORTCUT → REVOKE REMOTE AUTHORITY → INVALIDATE CURRENT EPOCH → TERMINATE REMOTE SESSION → LOCK GNOME → RESTORE PHYSICAL DISPLAY → RESTORE PHYSICAL INPUT → VERIFY → LOCAL_LOCKED`. Credential-compromise procedures are each separately enumerated with numbered steps: Suspected credential compromise generally (§22, 11 steps covering password/TOTP/Access-Key/trusted-device/recovery-codes/host-key); Suspected stolen trusted device (§23, 6 steps); Suspected Remote Access Key compromise (§24, 8 steps — "The old key must immediately cease to authorize new-device authentication"); Suspected TOTP compromise (§25, 7 steps); Suspected host compromise (§26, 12 steps, the most severe). Revoke-all (§32, id=`lry9ut`): increment/invalidate epoch → revoke all leases → terminate sessions → lock → restore display → restore input → verify. Disable remote access (§33) and Safe Mode (§34) are distinct but overlapping recovery mechanisms. Recovery after failed upgrade (§35), power loss (§36 — expected default `LOCAL_LOCKED`), kernel/GPU update (§37), and GNOME update (§38) each get dedicated numbered procedures, all ending in a mandatory readiness re-check before returning to supported operation. Evidence to collect (§28): host state, session/client/host ID, authentication result, lease state, security epoch, state transitions, component versions, systemd status, journal entries, GNOME/Mutter/PipeWire diagnostics, network info, display/input topology, emergency events — explicitly excluding passwords/TOTP secrets/Remote Access Keys/recovery codes/private keys/valid session credentials (§28, matching the task's doc-00 context verbatim).

**6. Tests/verification.** Recovery Verification Checklist (§49) — 22 items across 6 categories (Security 5, GNOME 4, Display 3, Input 3, Services 4, Compatibility 3). DoD (§58) — 16 unlabeled criteria. No formal test-ID scheme; anchors substitute for IDs as in the other three docs.

**7. Phase/sequencing guidance and DoD.** §56 Copilot Implementation Order (16 steps): `status/readiness → state visibility → active session visibility → session revocation → revoke-all → remote-access disablement → emergency status → compatibility/doctor → diagnostics → recovery orchestration → credential rotation workflows → trusted-device management → upgrade recovery → incident evidence collection → operational documentation → recovery regression tests`.

**8. Cross-references.** Uniquely explicit: §55 item 4 instructs "Read Documents 1–20" — the only place in these four documents where a numeric cross-document reference to the whole spec set appears (generic, not per-topic). `adaptive-workflow-configurator` at §55/L1342. Reuses doc 13's failure-classification/error-code concepts (§28 "relevant journal entries," §29 structured/redacted logs) and doc 14/15's "disable remote access" phrasing.

**9. Ambiguities, gaps, contradictions.** Two parallel state taxonomies coexist in the same document without an explicit mapping: **Operational States** (§3, line 57: `LOCAL_ACTIVE, LOCAL_LOCKED, REMOTE_ACTIVE, REMOTE_DEGRADED, TEARING_DOWN, RECOVERING, EMERGENCY, FAILED_SAFE, DISABLED, INCOMPATIBLE`) vs. **Operational Recovery Levels** (§50, line 1204: `LEVEL 0–5`). Implementers could conflate or duplicate these. The canonical CLI verb list at line 902 (`status, doctor, sessions, revoke-session, revoke-all, disable, enable, emergency-status, compatibility, diagnostics`) does **not** fully reconcile with doc 13's diagnostic-CLI list at line 789 or doc 14's recovery-verb list at line 1265 (see Doc 13 §9 and cross-document notes below). File ends mid-sentence at line 1469 ("The ultimate operational guarantee is:") with no closing statement — identical truncation pattern to doc 15.

**10. Risks/feasibility concerns.** §57's Copilot Stop Conditions is itself a candid feasibility admission: the spec authors acknowledge that guarantees like "revocation cannot be guaranteed," "physical display/input restoration cannot be verified," or "the system cannot establish a known safe state" might genuinely arise, and the prescribed response is to halt and escalate rather than force an unsound fix — implying these safety guarantees are not assumed to be trivially achievable. Emergency independence from gateway/network/main daemon is asserted repeatedly (§11, §18-19, §21) but the document never explains the underlying mechanism by which `remote-emergencyd` obtains physical input access independent of the compositor-mediated Wayland/libei input path — a nontrivial engineering gap. Lack of on-disk recovery marker files means every "verify state" step must re-derive truth live from GNOME/systemd/D-Bus, which is a bootstrapping risk if those very subsystems are degraded during the incident being recovered from.

### Contradictions between the four docs
1. **Three non-reconciled CLI vocabularies** for what may be one or several tools:
   - Doc 13 §23 (line 789): `status, health, capabilities, session, display, input, network, security, logs, self-test, version` — read-only diagnostics.
   - Doc 14 §46 (line 1265): `diagnose, repair, disable, reset, uninstall` — installer/recovery framing.
   - Doc 21 §40 (line 902) / §6 (line 150) / §31: `status, doctor, sessions, revoke-session, revoke-all, disable, enable, emergency-status, compatibility, diagnostics`, invoked as `remote-access status` / `remote-access sessions` / `remote-access revoke-session <session>`.
   
   Overlaps are thin: only `status` appears in all three; `disable`/`diagnostics` appear in two of three under different neighbors. `health` (13) vs `doctor` (21); `capabilities` (13) vs `compatibility` (21); `repair`/`reset` (14) appear nowhere else. None of the docs states whether these are one binary's subcommands, multiple binaries, or aspirational/illustrative phrasing only — each doc separately disclaims "exact names follow repository conventions."
2. **Two un-mapped state taxonomies inside doc 21 itself**: Operational States (§3, `LOCAL_ACTIVE...INCOMPATIBLE`, line 57) vs. Operational Recovery Levels (§50, `LEVEL 0–5`, line 1204).
3. **Unit-name asymmetry inside doc 15**: `remote-hostd.service`, `remote-gateway.service`, `remote-emergencyd.service` are literal (line 299), but `gnome-session-agent` gets only "appropriate user-session integration," no literal unit filename — internally inconsistent naming completeness for four sibling components.
4. **Formatting inconsistency**: docs 13, 15, 21 use `id="xxxxxx"` anchors on key code blocks; doc 14 uses **zero** such anchors (confirmed via grep) — suggests doc 14 was authored/passed through a different template than its siblings.
5. **Three near-identical but independently-worded truncated endings**: doc 14 line 1747 ("The most important first-run invariant is:"), doc 15 line 1460 ("The ultimate packaging invariant is:"), doc 21 line 1469 ("The ultimate operational guarantee is:") — all three files end mid-sentence with no closing statement/code block, while doc 13 alone closes properly with a complete final invariant block. This is a genuine completeness gap in the source documents themselves, not a reading artifact (verified against each file's true last line).

### 5 most decision-relevant insights for planning observability, install, packaging and ops phases
1. **No package name, no config file paths, no systemd unit name for `gnome-session-agent`, no signing technology (GPG/sigstore), and no packaging tool (dpkg/debhelper/cargo-deb) are defined anywhere in the spec.** These are first-order decisions the implementation plan must make explicitly before packaging/install work can start — they are not merely "left to convention," they are simply absent.
2. **The CLI surface is fragmented across three vocabularies with no reconciliation.** Before implementing any CLI, the plan should decide: one unified `remote-access` (or equivalent) binary with all verbs (`status/doctor/sessions/revoke-session/revoke-all/disable/enable/emergency-status/compatibility/diagnostics` plus read-only `capabilities/session/display/input/network/security/logs/self-test/version`), or a split diagnostic-vs-control tool. Doc 21's list is the most authoritative (it matches doc 00's summarized operational actions verbatim), so it should anchor the canonical decision, with doc 13's read-only verbs folded in as subcommands or a `--verbose`/read-only diagnostic mode.
3. **Emergency-controller independence is asserted as an absolute requirement across all four documents** (doc13 §2/§36F, doc14 §25/§27, doc15 §37, doc21 §11/§18-19/§57) but its implementation mechanism (how `remote-emergencyd` gets physical input access independent of the Wayland/libei/compositor input path) is never explained — this is the single highest-risk open engineering question spanning observability (must be diagnosable independent of gateway), install (must be verified before "READY"), packaging (must survive upgrade without a gap), and ops (must work when everything else is frozen).
4. **The safety invariant `REVOKE → LOCK → RESTORE → VERIFY` is completely consistent** across all four documents and doc 00 — this is the one thing implementers can treat as bedrock truth without further clarification, and it should be the shared core abstraction (a single "safe teardown" routine) invoked identically from disconnect, network failure, host-daemon crash, GNOME crash, upgrade, uninstall, emergency takeover, and incident response.
5. **All four documents explicitly defer implementation-technology choices** (installer language, logging format/library, CI system, signing mechanism, packaging tool, CLI framework) to "the project architecture" / "repository conventions" / `adaptive-workflow-configurator`. Since AGENTS.md/WORKFLOW_CONFIG.md in this repo currently only configure Python tooling (pytest/ruff/pyright) while doc 00 (per prior session context) prefers Rust for daemons, this is a live, unresolved decision the phase-wise plan must surface early rather than let each phase pick inconsistently.
