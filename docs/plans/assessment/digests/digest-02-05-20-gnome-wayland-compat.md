### 02 — GNOME 50+ / Wayland Feasibility PoC

**1. Purpose & scope.** Defines the *first* implementation phase — explicitly **not** the product — whose sole job is to experimentally answer: "Can an existing logged-in GNOME session be safely transformed into a remote-controlled session using a virtual display while the physical display and physical input are isolated, and can the system reliably fail back to a locked local console?" It prescribes 21 sequential ordinal experiments, a minimal state-machine prototype, and 8 lettered acceptance gates, and forbids proceeding to full product implementation until they pass.

**2. Named identifiers defined.**
- *D-Bus/Mutter/GNOME APIs* (colloquial names only — no fully-qualified `org.gnome.*` interface strings anywhere in the doc): "Mutter RemoteDesktop" (§4.1/L120), "Mutter ScreenCast" (§4.2/L138), `RecordVirtual` (§4.3/L151-159, explicitly "a private/unstable API"), "Mutter DisplayConfig" (§5/L174-176), `libei`, `libinput`, `uinput` (§16/§40).
- *Diagnostic tool fields* (§7): `User`, `Session ID`, `Type: wayland`, `Desktop: GNOME`, `GNOME version`, `Mutter version`, `PipeWire: AVAILABLE`, `RemoteDesktop/ScreenCast/RecordVirtual/DisplayConfig/libei: AVAILABLE/UNAVAILABLE`.
- *Resolutions/refresh*: `1280x720`, `1920x1080`, `2560x1440` (§10, §28); optional `1920x1080@120`, `2560x1440@120` (§28); baseline `30/60 Hz`.
- *Emergency identifiers*: shortcut `Ctrl + Alt + Shift + F12`, ~2‑second hold (§23-24); security epoch prototype `epoch = 1 → 2` with `lease.epoch` field (§25).
- *State machine* (§33, L975-983): `LOCAL_ACTIVE`, `LOCKED`, `REMOTE_AUTHENTICATING`, `REMOTE_PREPARING`, `REMOTE_ACTIVE`, `REMOTE_STOPPING`, `FAILSAFE` (heading also at L1021), `EMERGENCY`, `RESTORING_PHYSICAL_CONSOLE`.
- *Gates* (§47): Gate A Same session, B Virtual monitor, C Physical display isolation, D Remote input, E Physical input isolation, F Fail-safe, G Emergency takeover, H Same-session recovery — each must read `CONFIRMED`.
- *Evidence status vocabulary* (§43): `CONFIRMED / LIKELY / UNVERIFIED / UNSUPPORTED`.
- *Deliverable file paths* (§44-46): `docs/gnome/feasibility-report.md` (L1254), `docs/gnome/api-inventory.md` (L1285), `docs/security/poc-findings.md` (L1311) — **none of these exist in the current workspace** (no `docs/gnome/` or `docs/security/` folder present).
- *GPU categories*: `Intel`, `AMD`, `NVIDIA` (§30) — generic only, no driver/model names.
- *Component/module names*: **absent** — doc02 never uses `remote-hostd`, `gnome-session-agent`, `remote-emergencyd`, or `remote-gateway` (confirmed corpus-wide); it says "main remote agent," "main session agent," "emergency controller/daemon" instead.

**3. Hard requirements, gates and stop conditions.**
- MUST research current Ubuntu 26.04/GNOME 50 behavior before coding (§3); treat `RecordVirtual` as private/unstable and isolate it behind an abstraction (§4.3); capture/restore exact physical topology and prefer temporary over persistent config (§37-38); make cleanup transactional and idempotent (§35-36); disable remote input **before** slow cleanup steps; produce the 3 mandatory reports plus API inventory (§44-46); reach `CONFIRMED` on all 8 gates (§47).
- NEVER implement in this phase: Internet connectivity, rendezvous/STUN/TURN, production WebRTC, PAM/TOTP/Remote Access Key, trusted clients, production UI, file transfer, audio, clipboard, power management, multi-user, KDE, wlroots, X11 (§2); arbitrary shell execution; kernel modules/custom drivers/patches (§39); a global `/dev/input` grab "as the first solution" without evidence (§40); working around a fundamental blocker "by weakening the security requirements" (§48).
- Stop conditions (§48, 8 items): same-session control incompatible with GNOME 50 lock/session semantics; physical input cannot be isolated safely; physical display cannot be reliably isolated; failure cannot reliably fail closed; emergency takeover cannot operate independently; topology restoration unreliable; Mutter crashes/unstable in normal operation; required privileges unreasonably broad.

**4. Technology and library choices.** Only generic language guidance is given, and only here among the three docs: "**use Rust where practical**" (§41/L1174), plus "avoid unsafe code unless necessary," "isolate unsafe code," "document unsafe blocks," "use structured logging," "don't log secrets," "don't use arbitrary shell commands," "don't use `sudo` from inside the application," "don't run everything as root." **No specific crate is named** — no `zbus`, `pipewire-rs`, `gstreamer`, or `reis` anywhere in the file (verified).

**5. Experiments/tests/procedures specified.** All 21 are ordinal-named (no `EXP-NNN` ID scheme exists anywhere):
1. **First — Basic Session Discovery** (§7): non-destructive diagnostic reporting session/API availability.
2. **Second — RemoteDesktop** (§8): create/start/verify/terminate/verify-cleanup a session; record calls, IDs, errors.
3. **Third — ScreenCast** (§9): create session, get PipeWire stream, receive frames, report dims/rate, clean teardown.
4. **Fourth — Virtual Monitor** (§10): `RecordVirtual` at 1920×1080@60, then 1280×720/1920×1080/2560×1440.
5. **Fifth — Virtual Monitor as Active Display** (§11): desktop/apps/windows/workspace continuity on the virtual monitor.
6. **Sixth — Physical Display Isolation** (§12-13): snapshot→create/activate VM→disable physical→verify no active output→restore→verify exact topology.
7. **Seventh — Remote Input** (§14): synthetic key/pointer/button/scroll events reach terminal/editor/browser/window-move/modifiers.
8. **Eighth — Physical Input Isolation** (§15): physical devices inert, remote devices effective, simultaneously.
9. **Ninth — GNOME Lock** (§17): trigger/verify lock, apps survive, unlock, same session persists.
10. **Tenth — Same Session Continuity** (§19): build identifiable state, full remote cycle, verify state survives — called "a critical acceptance test."
11. **Eleventh — Normal Disconnect** (§20): `LOCAL_ACTIVE→REMOTE_PREPARING→REMOTE_ACTIVE→DISCONNECT`; input revoked→session terminated→locked→display/input restored; no auto-unlock.
12. **Twelfth — Abrupt Network Failure** (§21): kill connection; same convergence, no manual cleanup.
13. **Thirteenth — Main Agent Crash** (§22): `kill -9` on the session agent; determine automatic vs. manual recovery.
14. **Fourteenth — Emergency Controller** (§23): independent daemon, shortcut-triggered revoke/lock/restore/epoch-increment.
15. **Emergency Test** (§24) and **Security Epoch PoC** (§25): kill main stack, confirm shortcut still works; verify stale-epoch lease rejection.
16. **Fifteenth — Reconnect** (§26): new lease/VM, isolation re-applied, no forced logout.
17. **Sixteenth — Monitor Hotplug** (§27): plug/unplug during remote mode; Mutter/VM/topology/Shell stability.
18. **Seventeenth — Resolution/Refresh** (§28): matrix above; "particular attention" to high-refresh teardown.
19. **Eighteenth — Cursor** (§29): position/visibility/shape/no-desktop-damage; hw+sw paths.
20. **Nineteenth — GPU Matrix** (§30): Intel/AMD/NVIDIA parity pass.
21. **Twentieth — Suspend/Resume** (§31): "a safe failure is acceptable," no assumed survival.
22. **Twenty-First — GNOME Session Restart/Failure** (§32): must fail safely; document fallback if unrecoverable.
Evidence format (§43): `Experiment/Date/Ubuntu version/GNOME version/Mutter version/Kernel/GPU/Driver/PipeWire version/Objective/Procedure/Expected result/Observed result/Status/Issues/Workarounds/Security implications/Follow-up`.

**6. Mechanisms proposed for each hard problem.**
(a) *Virtual monitor*: `RecordVirtual` is the only candidate discussed; treated as private/unstable, isolated behind an abstraction (§4.3, §10).
(b) *Physical display disable/restore*: Mutter DisplayConfig for inspect/save/disable/restore/rollback (§5); explicit caveat that "disabled" ≠ "panel powered off" — must distinguish (1) pixels not routed, (2) panel reports no signal/standby, (3) panel may show hardware messages; restated requirement: "the active desktop must not be visible on the physical console during remote mode" (§13).
(c) *Remote input via libei/EIS*: libei named only as a research area (§16); this phase tests input via a local synthetic-event mechanism, not a committed libei implementation.
(d) *Physical input isolation candidates*: §16 lists Mutter input routing/libei/libinput/uinput/Wayland seat semantics/GNOME session lock state/physical seat handling/remote input authorization; §40 gives a second, overlapping-not-identical list (uinput/libinput interception/seat-level routing/minimal privileged helper) to evaluate only if native mechanisms prove insufficient — no ranked order is ever stated, only "research GNOME-native mechanisms first."
(e) *Lock semantics*: use GNOME's normal lock, no custom lock screen (§17); explicitly flags that "GNOME Remote Desktop's normal remote-assistance behavior may terminate remote access when the screen is locked" and this must not be assumed acceptable (§18) — presented as an open, possibly-fatal research question, not a solved mechanism.
(f) *Topology snapshot/restore*: procedure in §12; backup must include connector names (**not** assumed stable after hotplug), modes, layout, scale, transform, primary, "relevant properties" (§37); prefer temporary over persistent config, never touch `monitors.xml` permanently (§38).
(g) *Hotplug*: Sixteenth Experiment only defines the test procedure (§27); no mechanism is proposed — explicitly open/TBD.
(h) *GPU/driver*: Nineteenth Experiment (§30) — Intel/AMD/NVIDIA generic parity testing only; **no hybrid/PRIME/Optimus dual-GPU scenario appears anywhere in the document** (verified corpus-wide), a direct gap against the real host.

**7. Phase/sequencing guidance and definition-of-done.** Explicit linear order: research → session discovery → RemoteDesktop → ScreenCast → RecordVirtual → VM-as-active-display → physical display isolation → remote input → physical input isolation → GNOME lock → same-session continuity → normal disconnect → network failure → agent crash → emergency controller → reconnect → hotplug → resolution/refresh → cursor → GPU matrix → suspend/resume → GNOME restart → state-machine prototype → deliverables. ### 20 — Compatibility, Hardware, and GNOME Version Strategy

**1.
