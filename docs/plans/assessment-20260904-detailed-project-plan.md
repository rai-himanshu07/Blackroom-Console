## 1. Executive summary

1. **The specification set is unusually complete on *what* and *why*, and deliberately
   silent on *how*.** Every safety invariant, gate, threat, test class and operational
   procedure is stated at least twice across the 21 documents, and the safety chain
   `REVOKE → LOCK → RESTORE → VERIFY → LOCAL_LOCKED` is consistent in every document.
   Conversely, no document fixes a programming language, library, wire format, file path,
   numeric timeout, KDF, package name, or systemd unit for the session agent. These are
   not omissions to be discovered later; they are first-order decisions the plan must make
   before Phase 2 (see §6).
2. **The documents disagree with each other in identifiers, not in intent.** There are
   three phase-numbering schemes, three spellings of the fail-safe state, four
   session-state vocabularies, four compatibility-tier vocabularies, three CLI verb sets,
   two gate letterings (A–H feasibility vs A–J security), and a four-way control-lease
   schema conflict. §5 resolves each into one canonical form for this project.
3. **This workstation *is* the target platform**, which removes the largest usual risk for
   Phase 1: Ubuntu 26.04.1 LTS, GNOME Shell 50.1, Mutter 50.1, Wayland, PipeWire 1.6.2,
   libei/libeis 1.5.0, systemd 259, and `gnome-remote-desktop` 50.2 (installed, inactive)
   are present. Mutter exposes `org.gnome.Mutter.{DisplayConfig, RemoteDesktop,
   ScreenCast, InputCapture, InputMapping}`; GNOME exposes `org.gnome.Shell.ScreenShield`
   and `org.gnome.ScreenSaver`. Rust 1.96, Node 22 and cargo are installed; the GNOME
   development headers are not (§3).
4. **Two hard feasibility gates remain genuinely open and are correctly identified by the
   documents as potential project stoppers:** physical input isolation (Gate E) and GNOME
   lock/same-session semantics (Gate A/Phase 8). The host inventory surfaces a candidate
   the documents never mention — Mutter's `InputCapture` interface — which should be the
   first mechanism tried for Gate E (§7).
5. **One architectural clarification is required that the documents leave fuzzy:** the
   WebRTC media/input endpoint must live in the *user session* (where the PipeWire capture
   stream and EIS handle exist), not in the system-level `remote-hostd`. Authority stays
   in `remote-hostd`; enforcement of the lease per input event happens in the session
   agent against a `remote-hostd`-signed lease (§7.6).
6. **Stack decision (delegated by the user):** Rust for every daemon, helper and the CLI;
   TypeScript for the browser client; Rust-only tests (no Python). This matches the
   documents' stated preference ("use Rust where practical", `cargo audit`/`cargo deny`)
   and requires updating the Python command overrides in `AGENTS.md` (§6.1, §9).
7. **Recommended phase model:** Document 00's Phases 0–20 as the spine, Document 11's
   Phases 0–30 as sub-phases, Document 10's Experiments 0–38 as the executable content of
   Phases 1 and 3–10, grouped into five stages with a formal Go/No-Go decision after the
   GNOME feasibility stage. The phase-wise plan is in
   [plan-20260904-blackroom-console-master-roadmap.md](plan-20260904-blackroom-console-master-roadmap.md);
   the first executable plan is
   [plan-20260904-phase0-1-discovery-and-environment.md](plan-20260904-phase0-1-discovery-and-environment.md).

## 4. Document-set assessment

### 4.1 Roles and authority ordering

The documents form four layers. When two conflict, the lower-numbered layer here wins:

1. **Master prompt — Document 00.** Invariants INV-001…014, canonical component names,
   canonical 11-state vocabulary, hard gates A–H, phases 0–20, stop conditions, evidence
   classifications. Treated as the controlling document for this project.
2. **Normative architecture — Documents 03 (security, self-declared normative), 06
   (privilege model), 07 (state machine; "externally observable safety properties … must
   remain true"), 16 (protocol contracts), 17 (data model).**
3. **Domain specifications — 04, 05, 08, 09, 12, 13, 14, 15, 18, 19, 20, 21.**
4. **Planning/rationale — 01 (master plan; oldest, uses superseded state names), 02
   (feasibility PoC; superseded state names), 10 (experiment plan; canonical names), 11
   (development phases and DoD; canonical names).**

Documents 01 and 02 predate the canonical vocabulary and are the only ones using
`REMOTE_AUTHENTICATING / REMOTE_PREPARING / REMOTE_STOPPING / FAILSAFE / LOCKED /
RESTORING_PHYSICAL_CONSOLE`. They remain valuable for rationale and for Document 02's
experiment procedures, but their identifiers are superseded.

### 4.2 Strengths

- Safety semantics are consistent everywhere: fail closed; remote failure never unlocks;
  emergency wins and does not unlock; no valid lease → no input; epoch invalidation; no
  generic privileged execution; no black-window or headless-session substitutes.
- The experiment programme (Doc 10: Experiments 0–38, Gates A–H, result format, mock-first
  then real-system) is directly executable.
- Testing is layered and hardware-aware (Doc 12 Tiers 1–4; Doc 18's 82 `RT-*` attacks,
  `INV-SEC-001…010`; Doc 19's `INV-PERF-001…010` and `PERF-*` profiles).
- Definition-of-done templates exist per category (Doc 11 §36–41) and per document.
- The privilege model is concrete enough to start: four domains, zero D-Bus for the
  gateway, minimal emergency daemon, explicit forbidden interfaces.

### 6.4 Cryptography and secrets

| Item | Decision |
|---|---|
| Randomness | `getrandom`/`OsRng` only; `zeroize`/`secrecy` for in-memory secrets. |
| Host identity | Ed25519 keypair (`ed25519-dalek`), private key file `0600 remote-hostd`; fingerprint = SHA-256 of public key, displayed as grouped hex (Doc 14 §13). |
| Remote Access Key | 256-bit CSPRNG, base64url (Doc 03 §15); stored as **Argon2id** verifier (m=64 MiB, t=3, p=1) — Doc 17 §15; rotation = new generation + epoch increment (C7). |
| Recovery codes | 10 × 80-bit base32 codes, Argon2id-hashed, single-use (Doc 03 §57–59). |
| TOTP | RFC 6238 SHA-1/6 digits/30 s (authenticator-app compatibility), `totp-rs`; ±1 step skew; reject reuse of the same (step, code) pair; secret stored encrypted at rest with a key in `/var/lib/blackroom-console/secrets/` (file permissions are the primary boundary; kernel keyring/TPM sealing is deferred). |
| Session credential | 256-bit opaque bearer, stored server-side as SHA-256 hash with binding (host, user, client, session, epoch, expiry). No JWT. |
| Control lease | `ControlLease` (C5) **signed by the host identity key** so `gnome-session-agent` verifies lease/epoch/expiry locally on every input event without a round trip; `remote-hostd` can still revoke synchronously via IPC. |
| Trusted-device credential | Device keypair generated in the browser with WebCrypto as a **non-extractable** `CryptoKey` (ECDSA P-256 for cross-browser support; Ed25519 when available), stored in IndexedDB; host stores the public key; authentication = signed challenge. | TLS | `rustls` in `remote-gateway`; certificates: user-provided or a setup-generated CA/host certificate for LAN (Doc 04 §66); no pinning (Doc 04 §68). |
| Persistence | Files with atomic `write-tmp → fsync → rename → fsync(dir)` for every security record; `rusqlite` (bundled SQLite, WAL) **only** for sessions/audit if file-per-record proves insufficient (Doc 17 §44). Schema version field on every file. |

## 7. Feasibility risk register (Gates FEAS-A…H) with mechanism candidates

Ordered by risk. "Host lead" = evidence from this workstation not present in the documents.

### 7.1 FEAS-E — Physical input isolation (highest risk; hard stop if unachievable)

- **Requirement:** while `REMOTE_ACTIVE`, physical keyboard/mouse cannot control the
  session; remote input continues; emergency chord still works; hotplugged devices are
  covered; restoration verified (INV-008, INV-010, Doc 10 Exp 9/10/38, Doc 18 `RT-INPUT-*`).
- **Candidates, in research order:**
  1. **Mutter `org.gnome.Mutter.InputCapture` (host lead; not in any document).** Designed
     for KVM-style clients: once a capture is *activated*, the compositor delivers physical
     input to the capturing client over EIS and stops delivering it to the focused
     surface. If `gnome-session-agent` activates a capture with barriers enclosing the
     whole (virtual-only) layout and never releases it, physical input is isolated by a
     supported compositor mechanism with no extra privilege, and the agent can *observe*
     the emergency chord in the captured stream as a secondary trigger. Open questions
     for Experiment 9: does keyboard capture engage without a pointer barrier crossing;
     does capture persist across lock/unlock and hotplug; does `RemoteDesktop` EIS
     injection keep working while capture is active; does Mutter auto-release under any
     condition.
  2. **Mutter `RemoteDesktop`/`ScreenCast` session flags or `InputMapping`** — inventory in
     Experiment 2; likely insufficient alone.
  3. **Minimal privileged helper with `EVIOCGRAB`** on an allow-list of *physical* evdev
     devices (udev-tagged, seat0, excluding uinput/virtual nodes), udev-monitored for
     hotplug, exposing only `ISOLATE_INPUT`/`RESTORE_INPUT` (Doc 06 §42–45, §117). The
     grabber necessarily receives the events and therefore *is* the natural emergency-chord
     observer; if this path is chosen the helper and `remote-emergencyd` should be the same
     small binary. Fallback only if (1) fails; must pass Doc 06 §64 DoD for privileged code.
  4. logind `PauseDevice` semantics are not available to non-controllers — rejected.
- **Stop condition:** none of the above isolates input without a global grab or broad
  privilege → report per Doc 00 §49.

### 7.2 FEAS-A / Phase 8 — GNOME lock and same-session semantics (second-highest)

- **Requirement:** `LOCAL_ACTIVE → lock → remote authenticates → remote user unlocks GNOME
  through the remote path → REMOTE_ACTIVE (unlocked, but physical display/input isolated)
  → disconnect → lock → LOCAL_LOCKED`. Doc 02 §18 and Doc 05 §5/§58 flag that GNOME's
  remote-assistance behaviour may terminate remote sessions on lock.
- **Host leads:** `org.gnome.Shell.ScreenShield` (`Lock`, `GetActive`,
  `ActiveChanged`) and `org.gnome.ScreenSaver` are the concrete interfaces; logind
  `Session.Lock/LockedHint` for a compositor-independent lock trigger; `gnome-remote-desktop`
  50.2 source is the reference for how a RemoteDesktop session behaves across the shield.
- **Key experiments (Exp 11/12):** whether a `RemoteDesktop`+`ScreenCast(RecordVirtual)`
  session created *before* locking survives `ScreenShield.Lock`; whether EIS input reaches
  the unlock dialog; whether `RecordVirtual` streams the shield; whether unlocking via
  remote input re-enables physical outputs (it must not).
- **Decision gate:** Architecture Review #1 after Phase 8 (Doc 11 §47): PROCEED / MODIFY /
  STOP.

### 7.3 FEAS-B/C — Virtual monitor and physical display isolation

- **Mechanism:** `org.gnome.Mutter.ScreenCast.Session.RecordVirtual` (private/unstable,
  isolate behind `GnomeBackend`) → PipeWire node; then
  `org.gnome.Mutter.DisplayConfig.ApplyMonitorsConfig` (temporary method, never persistent
  `monitors.xml`) enabling only the virtual monitor. Snapshot via `GetCurrentState`
  (`DisplayBackup` schema, Doc 05 §29, keyed by connector+EDID serial, not index).
- **Host-specific risks:** hybrid GPU — the external HDMI output is on the NVIDIA card while
  Mutter's primary GPU may be Intel; "disabled" output vs panel-standby behaviour (Doc 02
  §13) must be verified per output; NVIDIA explicit-sync/hardware-cursor caveats (Doc 05
  §80, `MUTTER_DEBUG_DISABLE_HW_CURSORS=1` only as a documented, measured workaround).
  Whether Mutter permits a configuration with **zero physical monitors enabled** when a
  virtual monitor exists is the first thing Experiment 5/6 must establish; if it refuses,
  Gate C is at risk and Phase 5 stops.
- **Automatic restoration lead:** when the owning process dies, Mutter destroys
  session-bound `ScreenCast`/`RemoteDesktop` objects and the virtual monitor; whether it
  re-enables physical outputs by itself (no zero-monitor state) is decisive for crash
  recovery and for the emergency daemon's display-restore path (Exp 15/16).

### 7.4 FEAS-D — Remote input

- **Mechanism:** `org.gnome.Mutter.RemoteDesktop.Session.ConnectToEIS` → EIS fd → `reis`
  crate (Rust libei) → keyboard/pointer devices; absolute pointer mapped to the virtual
  monitor's logical region. Lease enforcement per event in the agent (§6.4).

### 7.5 FEAS-G — Emergency independence

- **Chord observation:** `remote-emergencyd` reads physical keyboards via evdev
  (`evdev` crate) as a dedicated system user in group `input` with `DeviceAllow=char-input
  r`, `PrivateNetwork=yes`, full Doc 06 §97 hardening; if the `EVIOCGRAB` helper path is
  chosen (§7.1 candidate 3) the observer *is* the grabber.
- **Actions performable without `remote-hostd` or the agent:** (a) persist an epoch-bump
  marker in `/var/lib/blackroom-console/state/` that `remote-hostd` honours on next start
  (never-decreasing epoch, Doc 06 §155); (b) lock via logind `Session.Lock` on the system
  bus; (c) stop `gnome-session-agent` (and thereby Mutter's session-bound virtual monitor
  and EIS devices) via `systemd1` user-manager control **or** `SIGTERM` to the unit's main
  PID — the exact system→user control path is the Phase 10 research item (Doc 06 §19
  matrix); (d) notify `remote-hostd` over `emergency.sock` if alive. Display restoration
  independent of Mutter is impossible by construction; the design relies on Mutter's
  behaviour when the virtual monitor disappears (7.3) plus a user-session fallback unit
  `remote-emergency-restore.service` started by the user manager on `EMERGENCY_TRIGGERED`.
- **Required proof:** Doc 10 Exp 21–24, Doc 06 §140 (hostd dead), `RT-EMERGENCY-004`.

### 7.6 Architecture clarification — where WebRTC media and input terminate

The PipeWire stream (from `RecordVirtual`) and the EIS handle exist only in the user
session. Therefore the **WebRTC peer (video track + input data channel) terminates in an
unprivileged user-session process** — `gnome-session-agent` itself in the PoC, split into a
child `remote-media` process (GStreamer `webrtcsink`/`webrtcbin`, `pipewiresrc`, VA-API/
NVENC/x264 encoders) in Phase 14 per Doc 06 §75–78. `remote-hostd` remains the sole
authority: it authenticates, issues the signed `ControlLease`, brokers signalling via the
gateway, and can revoke synchronously; the agent drops any input event whose lease/epoch/
expiry fails local verification. `remote-gateway` never sees media (DTLS-SRTP end-to-end
to the browser; TURN relays ciphertext, Doc 04 §30). This satisfies Doc 05 §41 ("exact
process boundary may differ") and Doc 06's privilege split.

### 7.7 Residual design questions to settle in their phases (not blockers now)

- End-to-end protection of the authentication payload from browser to host so a compromised
  gateway never sees the Linux password (Doc 03 §7 vs Doc 16 §11 which lists `password` in
  `AuthenticateRequest`): encrypt the credential envelope to the host public key (X25519 +
  AEAD) in the browser — Phase 12 design decision with security review.
- Whether `pam-auth-helper` needs root for `pam_unix` on Ubuntu 26.04 (Phase 1 research).
- Reconnect vs new-session policy default (Doc 04 §55 says new authorization event; Doc 16
  §56 permits `session resume` with re-verification): v1 default = **reconnect requires
  re-authentication**; `reconnect` capability is advertised `false` until Phase 15.
- Codec: H.264 first (Doc 01 §65) with capability negotiation; VP9/AV1 measured later.

## 8. Safety plan for running experiments on the development workstation

Documents 12 §52 and 18 §4 want destructive tests off the primary workstation; only this
machine is available. The plan therefore mandates, before Experiment 6 (disable physical
outputs) and Experiment 9 (isolate physical input):

1. **Out-of-band access:** `openssh-server` enabled on the LAN with key-only auth; SSH client
   on the tablet/phone (e.g., Termux) verified to reach the host — user action, Phase 1.
2. **Experiment watchdog:** every experiment binary that changes display or input state
   arms a `systemd-run --user --on-active=<N>s` (or in-process) restore timer *before*
   applying the change and disarms it only after operator confirmation over the
   out-of-band channel; default N = 45 s.
3. **VT fallback:** `Ctrl+Alt+F3` is documented as the manual fallback for display-only
   experiments; it is *not* relied upon once input isolation is active.
4. **Snapshot before every run:** `DisplayConfig.GetCurrentState` saved to
   `docs/experiments/evidence/` and `gsettings` display state backed up (never edit
   `monitors.xml`).
5. **`gnome-remote-desktop` stopped and masked** for the duration of RemoteDesktop
   experiments to avoid session conflicts (re-enabled afterwards).
