# 11 — Development Phases, Copilot Agent Workflow & Definition of Done

## 1. Purpose

This document defines how the project should be implemented.

It converts the preceding architecture and security documents into an execution sequence for GitHub Copilot Agent.

The goal is to ensure that the agent:

- researches before implementing;
- validates difficult assumptions experimentally;
- implements incrementally;
- tests every meaningful change;
- does not bypass security gates;
- does not prematurely build the complete product;
- preserves the existing repository workflow;
- produces reviewable increments;
- stops when an architectural assumption is disproven.

This document is an **implementation governance specification**, not merely a project plan.

---

# 2. Primary Development Principle

The agent must follow:

```text
RESEARCH
   ↓
DESIGN
   ↓
IMPLEMENT
   ↓
TEST
   ↓
VERIFY
   ↓
DOCUMENT
   ↓
NEXT GATE
```

Never:

```text
IDEA
  ↓
IMPLEMENT EVERYTHING
  ↓
HOPE IT WORKS
```

---

# 3. Repository Workflow

Before doing any implementation:

1. Inspect the repository.
2. Inspect the workflow/configuration generated by `adaptive-workflow-configurator`.
3. Identify:
   - development workflow;
   - project conventions;
   - testing conventions;
   - documentation conventions;
   - quality gates;
   - agent instructions;
   - existing tooling.
4. Follow that workflow.
5. Extend it only when necessary.
6. Do not replace it with a competing workflow.
7. Do not create duplicate planning/configuration systems.

The adaptive-workflow-configurator output is part of the project's development environment and must be treated as authoritative for repository organization.

---

# 4. Agent Operating Mode

The GitHub Copilot Agent should behave as an engineering agent rather than a code generator.

For every significant task:

```text

    ↓

    ↓

    ↓

```

The agent should not silently skip a phase.

# 7. Phase 2 — State Machine Core

Implement the platform-independent state machine.

Initial states:

```text
LOCAL_ACTIVE
LOCAL_LOCKED
PREPARING_REMOTE
REMOTE_ACTIVE
TEARING_DOWN
RECOVERING
EMERGENCY
FAILED_SAFE
```

Implement:

- states;
- events;
- legal transitions;
- illegal-transition handling;
- state-machine locking;
- transition IDs;
- structured events;
- idempotent cleanup;
- failure handling.

Use mocked platform adapters.

### Definition of Done

All legal transitions have tests.

All important illegal transitions have tests.

Concurrent-event behavior is tested.

No GNOME dependency is required to test the state machine.

# 8. Phase 3 — GNOME Session Discovery

Implement the GNOME session adapter.

It must reliably identify:

```text

UID
session ID

session type

```

Do not assume the first graphical session is the correct session.

### Definition of Done

The adapter reliably identifies the intended active GNOME session on the supported environment.

Prove:

```text
detect virtual monitor
```

### Definition of Done

Virtual monitor creation and teardown are reproducible.

# 11. Phase 6 — Remote Input

Implement the smallest possible remote-input proof.

- special keys.

### Definition of Done

Remote input reaches the intended GNOME session reliably.

---

# 12. Phase 7 — Physical Input Isolation

This is a hard gate.

Research and implement the safest viable mechanism.

Investigate:

```text
Mutter
libei/EIS
libinput
seat routing
uinput
minimal privileged helper
```

Do not implement a global `/dev/input` grab without demonstrating that it is necessary and safe.

Test:

```text
physical keyboard
physical mouse
USB hotplug
device reconnection
multiple input devices
```

### Definition of Done

Physical input cannot control the remote GNOME session while REMOTE_ACTIVE.

If this cannot be safely achieved:

> STOP.

Do not proceed to full product implementation.

# 13. Phase 8 — GNOME Lock Semantics

Experimentally establish the behavior of:

```text
remote control
+
GNOME lock
```

Determine exactly whether:

- remote capture continues;
- remote input continues;
- the session remains accessible;
- the remote connection terminates.

This phase must not rely on assumptions from GNOME Remote Desktop documentation alone.

### Definition of Done

The architecture's required lock behavior is experimentally classified as:

```text
SUPPORTED
PARTIALLY SUPPORTED
UNSUPPORTED
```

If the required behavior is impossible, stop and reassess the product architecture.

# 14. Phase 9 — Same-Session Lifecycle

Combine:

```text
GNOME session
+
virtual monitor
+
display isolation
+
remote input
+
session continuity
```

Demonstrate that the remote user is interacting with the same desktop session that existed before activation.

### Definition of Done

Same-session continuity is proven.

---

# 15. Phase 10 — Safe Teardown

Implement:

```text
revoke remote input
invalidate lease
restore physical input
restore physical display
destroy virtual display
lock GNOME
verify
```

Make every cleanup operation idempotent.

Test:

- normal disconnect;
- client crash;
- network loss;
- agent crash;
- partial cleanup failure.

### Definition of Done

Every tested teardown path reaches:

```text
LOCAL_LOCKED
```

or:

```text
FAILED_SAFE
```

Never silently `LOCAL_ACTIVE` when safety cannot be verified.

---

# 16. Phase 11 — Recovery Engine

Implement recovery independently of normal teardown.

The recovery engine should be capable of:

```text
invalidate remote authority
stop remote input
restore input
restore display
destroy virtual display
lock GNOME
verify
```

Test repeated recovery.

### Definition of Done

Recovery is:

- deterministic;
- bounded;
- idempotent;
- observable.

# 17. Phase 12 — Emergency Controller

Implement the smallest independent emergency mechanism.

Conceptually:

```text
physical hotkey
      ↓
remote-emergencyd
      ↓
revoke
      ↓
epoch++
      ↓
lock
      ↓
restore display
      ↓
restore input
```

The emergency mechanism must not depend on:

- browser;
- gateway;
- WebRTC;
- network;
- normal remote-session teardown.

### Definition of Done

Emergency takeover works while:

```text
main daemon healthy
main daemon stopped
network connected
network disconnected
browser connected
browser dead
```

# 18. Phase 13 — Security Epoch

Implement:

```text
current_security_epoch
```

Bind remote sessions and control leases to the epoch.

Test:

```text

epoch becomes N+1
old session rejected
```

### Definition of Done

No stale remote session can regain control after epoch invalidation.

# 19. Phase 14 — Control Lease

Implement short-lived control leases.

Lease contains:

```text

```

Implement:

- issue;
- renew;
- validate;
- revoke;
- expiration.

### Definition of Done

Remote input is impossible without a valid lease.

Lease expiration safely tears down remote control.

# 22. Phase 17 — Trusted Devices

Implement:

```text

```

Trusted devices must:

- remain subject to password + TOTP;
- have cryptographic credentials;
- be individually revocable;
- have associated sessions terminated when required.

### Definition of Done

A trusted device can connect without the Remote Access Key but cannot bypass TOTP.

# 42. Agent Stop Rules

Copilot Agent must stop implementation and report a blocker when:

```text
required GNOME capability does not exist
same-session behavior is incompatible
physical input cannot be isolated safely
physical display cannot be isolated
emergency takeover cannot operate independently
required privilege becomes excessive
recovery is unreliable
Mutter instability is unacceptable
security invariant cannot be enforced
```

The agent must not:

- weaken requirements;
- silently change architecture;
- remove safety checks;
- disable tests;
- mark a partial result as complete.

---

# 43. Research Stop Rule

Research should stop when sufficient evidence exists to make a technical decision.

Do not spend excessive time collecting redundant information.

Use this decision structure:

```text
Question
   ↓
Existing documentation
   ↓
Installed-system inspection
   ↓
Source inspection if necessary
   ↓
Minimal experiment
   ↓
Decision
```

---

# 44. Implementation Stop Rule

After each meaningful increment:

```text
run tests
inspect diff
inspect logs
verify behavior
update documentation
```

Do not accumulate a large untested implementation.

---

# 45. Commit-Level Guidance

Prefer small, coherent changes.

Good:

```text

Add display topology snapshot
Add input isolation experiment
Add lease validation
```

Avoid:

```text
Implement entire remote desktop
```

in one change.

The repository's configured workflow determines the exact commit/PR conventions.

# 50. Technical Debt Policy

Do not use technical debt as an excuse to weaken security.

Acceptable:

```text

```

Not acceptable:

```text

```

Security shortcuts must not be treated as normal technical debt.

# 57. Final Instruction to GitHub Copilot Agent

Treat Documents 01–11 as a coherent specification set.

Before implementing any significant feature:

1. Determine which specification governs it.
2. Inspect the repository and adaptive-workflow-configurator workflow.
3. Research any uncertain platform behavior.
4. Build the smallest useful increment.
5. Test both success and failure.
6. Verify security invariants.
7. Document observed platform behavior.
8. Do not silently weaken requirements.
9. Do not proceed past a hard feasibility gate without explicit evidence.
10. Keep privileged code minimal.
11. Keep the emergency path independent.
12. Keep GNOME-specific implementation isolated.
13. Keep the state machine authoritative.
14. Prefer safe failure over feature completeness.
15. Report blockers explicitly.

When uncertain between:

```text
"make it work"
```

and:

```text
"make it demonstrably safe"
```

choose:

```text
MAKE IT DEMONSTRABLY SAFE
```

# 58. Final Engineering Principle

The project should be developed as a sequence of **verified capabilities**, not as one large remote-desktop implementation.

The progression is:

```text
PROVE GNOME
    ↓
PROVE DISPLAY
    ↓
PROVE INPUT
    ↓
PROVE ISOLATION
    ↓
PROVE RECOVERY
    ↓
PROVE EMERGENCY
    ↓
PROVE SECURITY
    ↓
ADD NETWORKING
    ↓
ADD BROWSER UX
    ↓
HARDEN
    ↓
PACKAGE
    ↓
RELEASE
```

The hardest parts of the project are also the parts that determine whether the product idea is viable.

Therefore:

> **Never build around an unverified assumption when a small experiment can prove or disprove it.**

And:

> **Never trade a safety invariant for implementation convenience.**
