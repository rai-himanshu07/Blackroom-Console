# Secure GNOME Wayland Remote Console — Implementation Master Prompt

## 1. Mission

You are the primary implementation agent for this project.

Your job is to transform the project's engineering specifications into a working, secure, testable open-source remote-access system for a narrowly defined environment.

This is **not** a generic Linux remote-desktop project.

The core product is:

> A Wayland-native remote console for Ubuntu/GNOME that allows remote use of the user's existing GNOME session while physically isolating the workstation's display and input, and automatically returning the workstation to a locked local state when remote control ends or fails.

The defining product behavior is:

```text id="m0jv4x"
LOCAL ACTIVE
    |
    v
LOCK
    |
    v
AUTHENTICATE
    |
    v
ATTACH TO EXISTING GNOME SESSION
    |
    v
CREATE VIRTUAL DISPLAY
    |
    v
DISABLE PHYSICAL DISPLAY
    |
    v
DISABLE PHYSICAL INPUT
    |
    v
REMOTE ACTIVE
    |
    +----------------------+
    |                      |
    v                      v
DISCONNECT              FAILURE
    |                      |
    +----------+-----------+
               |
               v
       REVOKE REMOTE AUTHORITY
               |
               v
          LOCK SESSION
               |
               v
      RESTORE PHYSICAL DISPLAY
               |
               v
       RESTORE PHYSICAL INPUT
               |
               v
          VERIFY SAFE
               |
               v
         LOCAL LOCKED
```

The system must prioritize safety, authorization correctness, recovery, and reliability over convenience.

# 5. Absolute Safety Invariants

These are non-negotiable.

## INV-001 — No Authorization, No Remote Control

Without valid authentication and authorization:

```text
remote_input = false
```

---

## INV-002 — No Valid Lease, No Remote Input

A successfully authenticated client without a valid control lease must not be able to inject remote input.

---

## INV-003 — Lease Must Be Current

A lease must be bound to:

- session
- client
- host
- security epoch
- expiration
- permitted capabilities

Stale leases must be rejected.

---

## INV-004 — Epoch Revocation

When the security epoch changes, authority issued under the previous epoch must become invalid according to policy.

---

## INV-005 — Emergency Wins

Emergency takeover must invalidate current remote authority.

It must not wait for:

- browser
- network
- WebRTC
- gateway
- PipeWire
- normal remote agent

---

## INV-006 — Remote Failure Is Not Local Unlock

A remote disconnect or failure must never automatically unlock the physical workstation.

---

## INV-007 — Remote Failure Ends in Locked Local State

The intended safe endpoint is:

```text
LOCAL_LOCKED
```

or a precisely defined `FAILED_SAFE` state.

---

## INV-008 — Physical Input Isolation

While remote control is active:

```text
physical_keyboard → session = blocked
physical_mouse → session = blocked
```

This must be experimentally proven.

---

## INV-009 — Physical Display Privacy

While remote control is active, physical displays must not expose remote desktop content.

A black fullscreen window is not sufficient as the primary privacy mechanism.

---

## INV-010 — Physical State Restoration

When remote control ends:

```text
physical_display = restored
physical_input = restored
```

The restoration must be verified.

---

## INV-011 — Emergency Does Not Unlock

Emergency takeover must leave the GNOME session locked.

The user performs normal local authentication afterward.

---

## INV-012 — Stale Clients Cannot Reconnect

After emergency/revocation/epoch invalidation, stale browser sessions and credentials must not regain remote control.

---

## INV-013 — No Arbitrary Privileged Execution

No component may expose a generic:

```text
exec
shell
run-command
dbus-proxy
```

style privileged interface.

---

## INV-014 — Fail Closed

When a safety-critical condition cannot be determined confidently:

```text
remote_control = disabled
```

# 7. Architecture

Use strong privilege separation.

Conceptually:

```text id="r3y6mf"
                    INTERNET / LAN
                          |
                          v
                +--------------------+
                |  Remote Gateway    |
                |    UNPRIVILEGED    |
                +---------+----------+
                          |
                    authenticated IPC
                          |
                          v
                +--------------------+
                |    remote-hostd    |
                |   SYSTEM SERVICE   |
                +---------+----------+
                          |
                    authenticated IPC
                          |
                          v
                +--------------------+
                | GNOME Session Agent|
                |    USER SESSION    |
                +----+----------+----+
                     |          |
                  Mutter     PipeWire
                     |
                   libei

                +--------------------+
                | remote-emergencyd  |
                | MINIMAL SAFETY PATH |
                +--------------------+
```

Responsibilities must remain separated.

### `remote-gateway`

Unprivileged.

Responsible for:

- HTTPS
- WebSocket signalling
- browser communication
- WebRTC signalling
- network-facing protocol handling
- rate limiting
- forwarding authenticated requests

Must not:

- run as root
- directly manipulate privileged system state
- access secrets unnecessarily
- provide arbitrary D-Bus access
- execute arbitrary commands

### `remote-hostd`

System-level authority.

Responsible for:

- authentication
- PAM
- TOTP
- Remote Access Key
- trusted clients
- session credentials
- authorization
- control leases
- security epoch
- revocation
- state orchestration
- systemd lifecycle
- policy
- security logging

### `gnome-session-agent`

Normal GNOME user-session component.

Responsible for:

- GNOME session discovery
- Mutter integration
- virtual display
- ScreenCast
- RemoteDesktop
- PipeWire
- libei/EIS
- display isolation
- physical input isolation
- locking
- restoration
- session-state reporting

### `remote-emergencyd`

Minimal privileged safety component.

Responsible only for:

- physical emergency shortcut
- revocation
- emergency session termination
- epoch invalidation
- locking
- display restoration
- input restoration
- safe-state enforcement

Do not allow functionality creep into this daemon.

# 8. Authentication Contract

Every remote session requires:

```text id="1j4g4z"
Linux username
+
Linux password
+
TOTP
```

For a new/untrusted device:

```text id="9k2s2r"
Linux username
+
Linux password
+
TOTP
+
Remote Access Key
```

Trusted devices:

```text id="x4qz1s"
Linux username
+
Linux password
+
TOTP
+
trusted-device credential
```

TOTP is mandatory for every session.

Trusted-device status must never bypass TOTP.

A completely new device must be able to authenticate while the user is physically away from the workstation.

Do not make physical pairing mandatory for first access.

---

# 9. Remote Access Key

Use the UI term:

> Remote Access Key

not:

> API Key

Generate it automatically using cryptographically secure randomness.

Prefer at least 256 bits of entropy.

Do not:

- hard-code it
- log it
- put it in browser localStorage
- expose it in URLs
- store plaintext unnecessarily

Store a verifier where practical.

Support secure rotation.

---

# 10. TOTP

Use standard RFC-compatible TOTP.

Do not implement vendor-specific authentication.

Support standard authenticator applications through standard TOTP semantics.

TOTP setup should include:

- secure secret generation
- local display/QR
- verification
- secure storage
- recovery-code generation

Recovery must not accidentally bypass the Remote Access Key requirement for new devices.

---

# 11. Session Credentials

Authentication credentials and remote-session credentials must be separate.

After successful authentication:

```text
authentication
    ↓
authorized session
    ↓
short-lived session credential
    ↓
control lease
```

Do not use the Linux password, TOTP secret, or Remote Access Key as the ongoing remote-control credential.

---

# 12. Control Lease

Remote input requires a current control lease.

Conceptually:

```text id="qg7g3q"
host_id
user
client_id
session_id
security_epoch
issued_at
expires_at
capabilities
```

Every remote input operation must ultimately be authorized against the current lease/epoch/session state.

No valid lease means:

```text
remote_input = false
```

---

# 13. Security Epoch

Maintain a security epoch.

Increment/invalidate it when required by:

- emergency takeover
- global revocation
- credential compromise
- daemon restart where policy requires
- security reset
- host recovery

A credential/lease issued under an obsolete epoch must not regain authority.

Persist the epoch safely if required to preserve invalidation across restart.

---

# 14. Core State Machine

Implement an explicit state machine.

Primary states:

```text id="wqk18f"
LOCAL_ACTIVE
LOCAL_LOCKED
AUTHENTICATING
AUTHENTICATED
PREPARING_REMOTE
REMOTE_ACTIVE
REMOTE_DEGRADED
TEARING_DOWN
RECOVERING
EMERGENCY
FAILED_SAFE
```

Do not represent this state implicitly through scattered booleans.

State transitions must be:

- explicit
- observable
- testable
- idempotent
- concurrency-safe
- timeout-bounded

# 15. Remote Activation Transaction

Remote activation should conceptually perform:

```text id="p4y6ye"
1. Authenticate
2. Authorize
3. Create session
4. Obtain control lease
5. Verify current GNOME session
6. Snapshot physical display topology
7. Create virtual display
8. Prepare capture
9. Disable physical outputs
10. Isolate physical input
11. Verify display isolation
12. Verify input isolation
13. Start media transport
14. Verify remote input
15. Enter REMOTE_ACTIVE
```

If any safety-critical step fails:

```text id="q1dr4v"
ROLLBACK
→ REVOKE
→ LOCK
→ RESTORE
→ VERIFY
```

Do not enter `REMOTE_ACTIVE` prematurely.

---

# 16. Disconnect Transaction

Normal disconnect:

```text id="n3a8fb"
1. Stop accepting remote input
2. Revoke control lease
3. Terminate remote session
4. Stop media
5. Lock GNOME
6. Restore physical display
7. Restore physical input
8. Destroy temporary virtual display
9. Verify
10. LOCAL_LOCKED
```

The exact low-level ordering may be adjusted based on experimentally validated GNOME behavior, but the final security properties are mandatory.

# 18. Emergency Takeover

Default emergency behavior should be equivalent to:

```text id="v8x6g5"
Ctrl+Alt+Shift+F12
```

with an appropriate hold duration to reduce accidental activation.

Make it configurable.

The implementation must ensure the shortcut remains usable while physical input is otherwise isolated.

Emergency action:

```text id="0pq5jq"
REVOKE
→ INVALIDATE EPOCH
→ TERMINATE REMOTE SESSION
→ LOCK GNOME
→ RESTORE DISPLAY
→ RESTORE INPUT
→ VERIFY
→ LOCAL_LOCKED
```

Do not unlock the workstation.

# 48. Hard Feasibility Gates

Do not proceed to full product implementation until the following are experimentally demonstrated.

## Gate A — Same Session

Remote control uses the existing GNOME session.

## Gate B — Virtual Display

Virtual monitor can be created reliably.

## Gate C — Physical Display Isolation

Physical display cannot expose remote content.

## Gate D — Remote Input

Remote keyboard/mouse works.

## Gate E — Physical Input Isolation

Physical keyboard/mouse cannot control the session during remote mode.

## Gate F — Fail-Safe

Network/component failure revokes remote authority and reaches a safe state.

## Gate G — Emergency

Emergency controller works independently.

## Gate H — Same-Session Recovery

Disconnect/emergency restores the workstation correctly.

Failure of any hard gate requires investigation before proceeding.

Stop implementation and report clearly if:

- same-session architecture is incompatible with GNOME

# 76. Final Engineering Principle

Do not optimize for:

> "How quickly can we get a remote desktop working?"

Optimize for:

> **"How confidently can we prove that remote control is temporary, authorized, isolated, revocable, recoverable, and incapable of leaving the physical workstation in an unsafe state?"**

The system should assume:

```text
NETWORKS FAIL
CLIENTS FAIL
BROWSERS FAIL
GATEWAYS FAIL
PROCESSES CRASH
GNOME FAILS
MUTTER CHANGES
PIPEWIRE FAILS
GPUS FAIL
DEVICES CHANGE
CREDENTIALS LEAK
RESOURCES RUN OUT
```

The architecture must remain safe anyway.

The final invariant is:

```text id="k4z6j1"
REMOTE CONTROL
     =
TEMPORARY
+
AUTHENTICATED
+
AUTHORIZED
+
SESSION-BOUND
+
LEASE-BOUND
+
EPOCH-BOUND
+
REVOCABLE
+
FAIL-CLOSED
```

And the ultimate recovery invariant is:

```text id="w0y7h3"
ANY REMOTE FAILURE

        |
        v
LOCK GNOME
        |
        v
RESTORE PHYSICAL STATE

VERIFY
        |

LOCAL LOCKED
```

**Never trade a safety invariant for implementation convenience.**

**Never replace an unverified assumption with a guess.**

**Never mark an untested security property as verified.**

**Never allow remote-control authority to outlive the conditions under which it was granted.**
